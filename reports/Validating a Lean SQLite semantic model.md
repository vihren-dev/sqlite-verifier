# Prove fewer tests, generate many more

Your idea is feasible, and every prior formal semantics that claimed to match a real system was validated the same way. What needs to change is the balance. The cases you prove in Lean with `decide +kernel` should be a curated regression layer of a few hundred to a few thousand cases. They sit on top of a much larger stream of cases that the *compiled* Lean model runs differentially against the pinned SQLite 3.51.0 binary. No precedent I found (Cedar, EVMYulLean, LNSym, SQLCert, SibylFS, WasmCert) kernel-checks its whole conformance suite. They all run extracted or compiled code at 10⁴–10⁷ inputs and prove general theorems separately. SQLite's own Tcl suite is a good source if you **observe it running rather than parse it**. Run the upstream `.test` files under a logging proxy of the `sqlite3` Tcl command, cut each assertion into a self-contained case, minimize it, and re-derive typed expected results from the native binary. For your roadmap scopes (ALTER, constraints, indexes, DML, transactions, types) that should yield roughly 3k–6k cases. For validation beyond tests, the useful approaches are schema-aware random differential testing, metamorphic laws proved once as Lean theorems, a coverage build of SQLite restricted to the functions your subset reaches, R-ID requirement traceability, and mutation testing of the model. None of this proves the model matches SQLite. The aim is to make the remaining disagreements rare, well localized, and explicitly recorded.

## The per-case proof works, but only as the top tier

The mechanics are sound for your trust policy. `decide +kernel` reduces through everything, including well-founded recursion that plain `decide` refuses to unfold, and it evaluates the `Decidable` instance only once ([lean4 Init/Tactics.lean @ v4.33.0](https://github.com/leanprover/lean4/blob/v4.33.0/src/Init/Tactics.lean)). It adds no axioms beyond those your model already uses. `native_decide` is ruled out. **Since Lean 4.29 each native computation is admitted as its own fresh axiom** ([Lean 4.29.0 release notes](https://lean-lang.org/doc/reference/latest/releases/v4.29.0/)), named like `t1._native.native_decide.ax_1_1`, which falls outside the propext/Classical.choice/Quot.sound allowlist and cannot be meaningfully replayed by Nanoda. A CI check that fails whenever `#print axioms` on a test theorem mentions `_native` enforces this cheaply.

Cost is what pushes you to tiers. In local micro-benchmarks on Lean 4.34.1, a 1,000-row insert-then-count query took about 0.17 s under `decide +kernel`. **500 small test theorems in one file took 7.6 s wall and about 840 MB RSS, against 2.3 s for the same checks as `#guard`.** Every change to the model invalidates every generated test module. Kernel-checking 10⁴ cases on every model edit is therefore the wrong loop, while a few hundred per shard, built in parallel by Lake, is fine. The industry pattern agrees. EVMYulLean passes 22,330 of 22,332 Cancun execution tests through a compiled `lake test` driver ([Nethermind](https://www.nethermind.io/blog/a-trustworthy-formal-model-of-evm-yul-in-lean); [EVMYulLean](https://github.com/NethermindEth/EVMYulLean)). Cedar's compiled Lean model ran at a median 6 µs per case against 10 µs for the Rust implementation during differential testing ([arXiv 2407.01688](https://arxiv.org/html/2407.01688)). SQLCert likewise validated 10,000 random queries by running OCaml extracted from Coq, not by evaluating inside Coq ([SQLCert preprint](https://easychair.org/publications/preprint/XGg9/open)).

Four representation choices decide whether kernel evaluation stays cheap, and all of them follow from what the kernel can reduce.

**Replace `Database := String → Option Table` with a first-order association list.** A function-typed database cannot be compared by `decide` and builds nested closures that the kernel re-reduces on every lookup. In the same experiments, `Std.HashMap` lookups got stuck under `decide +kernel`, while `Std.TreeMap` worked but ran slower than lists at test sizes.

**Keep REAL as `UInt64` bits and INTEGER overflow checks on bounded `Int`.** Lean 4.33 gives `Float` a kernel-reducible model for + − × ÷, sqrt, and comparisons, but `toString`, `floor`, `pow`, and the transcendental functions stay opaque ([Float.lean @ v4.33.0](https://github.com/leanprover/lean4/blob/v4.33.0/src/Init/Data/Float/Float.lean)). SQLite's REAL↔TEXT conversions therefore have to be written in Lean over `Nat`/`Int`, which the kernel evaluates with GMP ([Lean reference: Natural Numbers](https://lean-lang.org/doc/reference/latest/Basic-Types/Natural-Numbers/)).

**State each test as `checkCase c = true` with a `Bool`-valued checker.** The same function then runs under the kernel, `#guard`, and the compiled harness, so a disagreement between tiers flags an `@[extern]`/`@[implemented_by]` inconsistency rather than a test-encoding difference. Avoid `Decidable` instances built with `rw`/`simp`, whose `Eq.rec` terms block reduction.

**Test string-literal replay in Nanoda early.** Comparator's `Lean.Replay` currently rejects proofs that reduce string literals, although lean4checker and Nanoda accept them ([comparator #93](https://github.com/leanprover/comparator/issues/93)). Your TEXT-as-`List UInt8` choice already avoids this for values. Names stored as `String` do not.

## Mine SQLite's Tcl suite by running it, not parsing it

The upstream suite is large and mostly relevant. On `version-3.51.0` there are 1,174 `.test` files. Trunk has about 31k `do_test`, 14k `do_execsql_test`, and 1.5k `do_catchsql_test` call sites, and 77 DDL/DML/transaction/constraint/index/type/expression files hold about 4,260 of them ([sqlite/sqlite test/](https://github.com/sqlite/sqlite/tree/master/test)). sqlite.org reports 51,445 distinct Tcl cases ([How SQLite Is Tested](https://www.sqlite.org/testing.html)). Your bounded static extractor imports 3 of alter3.test's 59 call sites, and that ratio shows the ceiling of static parsing. **774 of the 1,195 trunk files use `ifcapable` and 389 use `foreach`**, and SQL is built with Tcl substitution inside helper procs. Turso's static Tcl-to-`.sqltest` converter documents the same wall: it "is not always accurate" and loops must be unrolled by hand ([Turso testing skill](https://smithery.ai/skills/tursodatabase/testing)).

The robust route is dynamic, and Turso has shown the key trick scales. Turso vendors 846 upstream `.test` files and runs them by implementing the `sqlite3` Tcl command over its own engine ([tursodatabase/turso](https://github.com/tursodatabase/turso)). You would do the same thing over *real* SQLite 3.51.0, with a proxy that logs instead of reimplementing. The proxy renames `sqlite3`, and its per-connection command records every `eval`/`onecolumn`/`exists` call with its SQL, success or error code and message, and connection name. `do_test` is redefined to emit test-boundary markers; the `do_execsql_test` and `do_catchsql_test` wrappers funnel into it automatically ([tester.tcl](https://github.com/sqlite/sqlite/blob/master/test/tester.tcl)). `db trace_v2 … statement` catches SQL that helper procs issue ([tclsqlite.c](https://github.com/sqlite/sqlite/blob/master/src/tclsqlite.c)). Loops, `ifcapable` branches, and substitution then resolve themselves, because you record what actually ran on the pinned build.

A test case is then the ordered list of statements on `db` since the last `reset_db` or reopen, followed by the assertion's SQL. Failed statements are kept because they can have partial effects inside a transaction. Delta-debugging against your native runner removes every statement whose absence leaves the assertion's typed result unchanged, which turns the shared-per-file database into independent empty-database cases, exactly your format. Tag and exclude cases that use a second connection (`db2`), file bytes (`hexio_*`), `db func` user functions, fault injection, or `do_eqp_test` query plans. **Never use the Tcl expected lists as proof targets.** `execsql` returns a flat untyped list in which NULL renders as an empty string, integer 1 and text '1' look identical, and `catchsql` returns message text without an error code ([tester.tcl](https://github.com/sqlite/sqlite/blob/master/test/tester.tcl)). Use the Tcl expectation only to confirm that the case extracted correctly. The Lean expectation should come from re-running the minimized case natively with `typeof()`, `quote()`/`hex()`, and `sqlite3_extended_errcode`.

| Source | Size | Best use for this model | Caveat |
|---|---|---|---|
| Tcl suite via logging proxy | ≈4.3k call sites in 77 relevant files; [estimate] 3k–6k usable cases | ALTER/rebuild, constraints, indexes, DML, transactions | Needs native re-oracling; exclude multi-connection and file-level cases |
| `e_*.test` evidence files | 601 distinct R-IDs cited ([test/](https://github.com/sqlite/sqlite/tree/master/test)) | Requirement-tagged cases; `e_createtable` already started | Public Tcl evidence covers only 870 of 3,487 requirements ([matrix](https://www2.sqlite.org/matrix/matrix.html)) |
| Turso `.sqltest` | 348 files, 9,302 isolated tests; `alter_table.sqltest` has 223 ([dsl-spec](https://github.com/tursodatabase/turso/blob/main/testing/sqltest/docs/dsl-spec.md)) | Cheap pre-isolated inputs | Expectations may reflect Turso, not 3.51.0; re-oracle; check license |
| sqllogictest | 7.2M queries, 225k statements; `evidence/` has 318 queries ([gregrahn mirror](https://github.com/gregrahn/sqllogictest)) | Expression/SELECT phase only | Stringly typed, 13.5% hash-only, and explicitly excludes transactions ([about.wiki](https://www.sqlite.org/sqllogictest/doc/trunk/about.wiki)) |
| `fuzzdata*.db` | ≈46k garbled scripts, no expected output ([test/](https://github.com/sqlite/sqlite/tree/master/test)) | Later: parser/error-path differential inputs | No oracle value |

The requirement matrix tells you where the public suite runs out, and it runs out exactly where a migration verifier cares most. `datatype3` (type affinity, 99 requirements), `lang_transaction` (27), and `lang_createindex` (17) have **zero** public Tcl evidence, and `lang_altertable` has Tcl evidence for only 9 of 21 ([requirement matrix](https://www2.sqlite.org/matrix/matrix.html)). Most of that coverage lives in the proprietary TH3 ([TH3](https://sqlite.org/th3.html)). You will have to write those cases yourself. Because R-IDs are an MD5 of the normalized sentence, produced by `docsrc/matrix.tcl` ([matrix.tcl](https://www.sqlite.org/docsrc/file/matrix.tcl)), you can regenerate the exact 3.51.0 requirement list and target it sentence by sentence, extending your existing five R-ID traceability entries into a coverage matrix. Pin extraction to the `version-3.51.0` tag. Trunk already contains `altercons*.test`, which does not exist in 3.51.0.

## Generated differential testing does the work that no corpus can

A mined corpus reflects what SQLite's authors thought to test. A generator reaches combinations nobody wrote down. SibylFS, the closest analogue because it too drives a stateful API with command sequences, put it bluntly: with an executable oracle "we do not have to manually determine the intended outcome for each test, but rather can focus on generating tests with good coverage." It checked 21,070 scripts in about 79 s ([SibylFS](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)). The Prolog SQL-semantics conformance work used a formal reference as a differential oracle and found 19 bugs and 11 inconsistencies across MySQL, TiDB, SQLite, and DuckDB ([arXiv 2406.09469](https://arxiv.org/abs/2406.09469)). In your setup the direction is reversed: SQLite 3.51.0 is ground truth and the model is on trial.

Generate *model AST terms* and pretty-print them to SQL, so every program is in scope by construction and constructor coverage is directly measurable. Cedar's lesson is to run two generators. A type-directed one builds a schema first, then conforming data and statements, and gave "deeper coverage of core logic and faster bug discovery". A second one is allowed to violate types and constraints so that error paths get exercised ([arXiv 2407.01688](https://arxiv.org/html/2407.01688)). ShardStore adds **argument bias**: prefer names that exist and values at corner cases ([ShardStore](https://www.cs.utexas.edu/~bornholt/papers/shardstore-sosp21.pdf)). For SQLite the corner cases are '1', ' 1', '1.0', 1e20, ±0.0, NaN-producing expressions, integers at 2⁶³, empty TEXT versus empty BLOB, and the 2000-column limit. Python Hypothesis's `RuleBasedStateMachine` is the pragmatic driver. Its `Bundle`s carry table and column names, `consumes()` models DROP, and failing runs shrink automatically to a minimal statement sequence ([Hypothesis stateful](https://hypothesis.readthedocs.io/en/latest/stateful.html)). Routing every generated statement through your production parser into the Lean AST prevents the generator from drifting from the model. Lean-side Plausible ([plausible](https://github.com/leanprover-community/plausible)) is better suited to properties that need no SQLite oracle. SQLancer's SQLite generator (MIT) is worth adding later as a filtered diversity source: keep only programs your parser translates ([sqlancer](https://github.com/sqlancer/sqlancer)).

After *every* statement, compare the statement outcome (OK, or error with its primary and extended code) and a canonical state dump. The dump covers `sqlite_schema` ordered by name, then each table's rows ordered by rowid as `(rowid, typeof, quote/hex)` tuples, then autocommit state. Comparing full state per step, rather than only query results, is unusual, but it is cheap for small random databases and localizes a divergence to one statement. Make "model returns Unsupported" a third verdict that never counts as agreement. Reduce each disagreement in two layers: statement-level delta debugging with a predicate that keeps the *same* disagreement signature (to avoid slipping onto a different bug), then AST-level shrinking ([SQLancer reducers](https://gist.github.com/ColinYoungTaro/df271b8683b526a6a73b568ce721b5e2); [arXiv 2402.04623](https://arxiv.org/pdf/2402.04623)). Then normalize identifiers and freeze the case as a proven Lean regression theorem. Cedar keeps a minimized fuzz corpus in CI and ships no release unless model, proofs, and differential tests are current ([AWS Open Source blog](https://aws.amazon.com/blogs/opensource/lean-into-verified-software-development/)).

## Prove the laws once and measure what the tests miss

Some properties quantify over all databases and should be theorems, not test cases. SQLancer's oracles are metamorphic laws that need no expected value. TLP says a query equals the disjoint union of its `p`, `NOT p`, and `p IS NULL` partitions ([OOPSLA'20](https://dl.acm.org/doi/abs/10.1145/3428279)). NoREC and DQE say that SELECT, UPDATE, and DELETE with the same predicate touch the same rows ([arXiv 2007.08292](https://arxiv.org/pdf/2007.08292); [survey 2311.06728](https://arxiv.org/pdf/2311.06728)). Each law can be used twice: proved about the model in Lean and run as a property against SQLite. For your current subset, the laws are that `BEGIN; S; ROLLBACK` is the identity, that a statement failing with default ABORT leaves state unchanged, and that `ADD COLUMN c DEFAULT d` preserves row count, rowids, and old columns while the new column reads `d`. The next scope adds rename-then-inverse-rename as the identity on data, and INSERT…SELECT into an empty clone as a copy. Proofs and tests catch different bugs. Cedar's validator non-termination bug surfaced only while constructing the termination proof, because random testing's chance of triggering it was "extremely low" ([arXiv 2407.01688](https://arxiv.org/pdf/2407.01688)). The Cedar results also argue for parser round-trip tests: `parse ∘ toSQL = id` over the AST is cheap, and round-trip testing found 8 of Cedar's 21 testing-discovered bugs.

Coverage has to be measured on both sides, because neither side alone tells you when you are done. On the SQLite side, build 3.51.0 with gcov and `SQLITE_COVERAGE_TEST` (which folds the `ALWAYS`/`NEVER` defensive branches, as SQLite's own 100% branch-coverage builds do ([testing.html](https://sqlite.org/testing.html))). Then report branch coverage only for the functions your subset reaches, such as `sqlite3AlterFinishAddColumn`, `sqlite3Insert`, `sqlite3Update`, `sqlite3EndTable`, and the affinity and comparison helpers. An uncovered branch there is either a missing test or a case the model lacks. On the model side there is no off-the-shelf Lean coverage tool, so log which AST constructors, error variants, and evaluator match arms each corpus exercises. SibylFS reached 98% statement coverage of its model this way and annotated unreachable lines ([SibylFS](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)). Cedar found that full line coverage still left 35.5% of generated conditions as boolean literals ([arXiv 2407.01688](https://arxiv.org/pdf/2407.01688)), and QPG found code coverage a weaker guide than query-plan diversity ([arXiv 2312.17510](https://arxiv.org/abs/2312.17510)), so treat coverage as a work list, not a finish line. Mutation testing of the model is the strongest measure of suite strength. It is DIY in Lean: flip a comparison, drop a constraint check, or alter the affinity table, then count how many mutants the differential suite and the proven tests kill, recording separately which mutants only the proofs catch. This mirrors SQLite's own branch-mutation practice ([testing.html](https://sqlite.org/testing.html)).

The last validator is human audit. JSCert commented every rule with the ES5 line it transcribes, so that spec authors could proof-read the model ([JSCert](https://www.chargueraud.org/research/2013/js/jscert_popl.pdf)). Tag Lean definitions with the R-IDs and doc URLs they implement. Where the docs are silent, cite the observed 3.51.0 test case as the spec. SQLCert did the equivalent when the SQL Standard was "of no help" on aggregates ([SQLCert](https://easychair.org/publications/preprint/XGg9/open)).

## Recommended pipeline and what to build first

The pipeline has four tiers sharing one case format. That format is a JSON record holding the SQL text, the parsed Lean term, the native SQLite per-statement trace with typed state dumps, and the R-ID tags.

| Tier | Input | Runs | Assurance |
|---|---|---|---|
| 1. Bulk differential | Hypothesis and Lean generators, plus mined Tcl, Turso, and SLT cases | Compiled `lake exe` model over JSON lines vs. native 3.51.0, on every change and nightly at scale | Compiled code agrees; trusts the Lean compiler |
| 2. Proven regression | Minimized disagreements, R-ID-tagged e_* cases, hand-written requirement cases | `decide +kernel` theorems, sharded 100–300 per module | Kernel-checked model behavior |
| 3. Independent replay | Tier 2 `.olean`s | lean4export + Nanoda, nightly | Second kernel |
| 4. General laws | Rollback, atomicity, ADD COLUMN, TLP/DQE | Lean theorems plus properties against SQLite | Holds for all inputs of the model |

The next steps below are ordered by value per effort, given what already exists in the repo.

| Priority | Step | Why now |
|---|---|---|
| 1 | Change `Database` to a first-order association list; add `checkCase : Case → Bool`; add a CI axiom check banning `_native` | Everything downstream depends on cheap, comparable kernel evaluation |
| 2 | Build the compiled `lake exe` runner and a per-statement state-dump comparator next to the existing native runner | Enables tier 1; reuses the translator and Tcl-config replication |
| 3 | Write a Hypothesis state machine for the current subset (CREATE, ADD COLUMN, INSERT, UPDATE, transactions), with well-scoped and error-seeking modes | Finds model bugs in the existing ~1,800 lines within days |
| 4 | Build the logging-proxy extractor, pilot it on alter3 and altertab/altercol/alterdropcol at 3.51.0, then add minimization and typed re-oracling | Replaces the bounded static extractor; calibrates the 3k–6k estimate |
| 5 | Prove the rollback-identity, statement-atomicity, and ADD COLUMN preservation laws | Cheap now, before rebuild semantics grow the model |
| 6 | Regenerate the 3.51.0 requirement list; target the zero-Tcl-evidence areas (datatype3, lang_transaction, lang_createindex, lang_altertable) with hand-written R-ID cases | These are the areas your roadmap enters and the public suite does not cover |
| 7 | Add a gcov-instrumented SQLite build, model rule-coverage logging, and parser round-trip tests | Turns "enough tests?" into a measurable work list |
| 8 | Later: mutation testing, a filtered SQLancer stream, SLT for the expression phase, and Nanoda replay of the full tier-2 suite | Expensive; pays off once the subset stabilizes |

## Conclusion

Correspondence cannot be proved without verifying SQLite itself, so the question to ask of each validation method is which disagreements it would have found. The oracle has its own weaknesses. SQLite's result order without ORDER BY, which of several simultaneous constraint violations it reports, its message text, and its rowid choice after deletes or at the maximum rowid are all implementation facts, not documented semantics. The model must either commit to them deliberately or return a set of allowed outcomes, as SibylFS did ([SibylFS](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)). Running each case under `PRAGMA reverse_unordered_selects` separates specified order from accidental order. Each disagreement will be one of four things: a model bug, a harness or normalization bug, a documentation gap, or a SQLite quirk you choose to model. SibylFS's nine Linux failures were all harness artifacts, and Cedar dropped a language feature over one mismatch ([arXiv 2407.01688](https://arxiv.org/pdf/2407.01688)). A classified mismatch log is part of the model's specification.

The more important shift is in what the kernel proofs are for. Proving a test case in Lean certifies that the *model* produces an answer. It does not certify that the answer matches SQLite, since that match rests entirely on the native re-oracling step. The proven tier is therefore valuable as a frozen, independently replayable record of decisions ("this is what 3.51.0 does, and the model is pinned to it"), while breadth comes from the compiled differential tier. Proving thousands of cases buys less than generating a million, provided the generator and the dumps are well designed.
