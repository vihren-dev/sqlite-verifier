# How prior formal semantics of SQL and real-world systems were validated against real implementations

Scope: precedents where a formal or executable model was checked against a real system without verifying that system's source code. The aim is methodology a Lean 4 model of SQLite 3.51.0 can borrow. Researched 2026-09-29. Primary PDFs (Guagliardo & Libkin, Benzaken & Contejean, SibylFS, Cedar FSE'24, JSCert, WasmCert, SpecTec, ShardStore) were downloaded and the validation sections read directly.

## Q1. Formal SQL semantics: what was modeled, and how was it validated against real DBMSs?

### Takeaway
Every SQL formalization that claims fidelity to real engines validated it the same way. They made the semantics executable, generated thousands to 100,000 random queries plus random small databases, and compared the model's output with real engines (PostgreSQL, Oracle) using bag equality. In every case the engines' deviations from the SQL Standard forced per-engine variants of the semantics. None of these projects formalized SQLite specifically. The closest is TRAF (ESOP 2025), which models type conversions, including SQLite's, and validated them with random queries.

### Cited Findings

**Guagliardo & Libkin, "A Formal Semantics of SQL Queries, Its Validation, and Applications" (PVLDB 11(1), 2017)**
- Covers SELECT-FROM-WHERE with nesting, bag semantics, NULLs and 3-valued logic. The authors say a formal proof of correctness against real RDBMSs is infeasible, "which leaves open one route: experimental validation" — [PVLDB paper](http://www.vldb.org/pvldb/vol11/p27-guagliardo.pdf)
- Correctness criterion: the two results must have the same number of columns, with the same names in the same order, and the same rows with the same multiplicities. Row order is ignored (bag equality) — [PVLDB paper](http://www.vldb.org/pvldb/vol11/p27-guagliardo.pdf)
- The query generator was shaped by TPC-H statistics. TPC-H queries use on average 3.2 tables, rarely more than 8 WHERE conditions, and at most 3 levels of nesting. The generator was parameterised with tables=6, nest=3, attr=3, cond=8 — [PVLDB paper](http://www.vldb.org/pvldb/vol11/p27-guagliardo.pdf)
- The semantics was implemented in Python purely as a validation oracle, not for performance. There were two variants: one for PostgreSQL's compositional `SELECT *`, and one for Oracle's syntax (`MINUS` instead of `EXCEPT`) — [PVLDB paper](http://www.vldb.org/pvldb/vol11/p27-guagliardo.pdf)
- Scale: a fixed schema R1..R8 with all-int columns, chosen "to avoid type checking and therefore simplify query generation". 100,000 random queries, each with its own random database generated by DataFiller. Base tables were capped at 50 rows because the reference implementation computes Cartesian products — [PVLDB paper](http://www.vldb.org/pvldb/vol11/p27-guagliardo.pdf)
- Result: "The results were always the same." Where Oracle raised an error on ambiguous `SELECT *` references, the Oracle variant of the semantics also raised an error, because the environment was undefined. **Error behaviour counted as an observable outcome to match** — [PVLDB paper](http://www.vldb.org/pvldb/vol11/p27-guagliardo.pdf)

**Benzaken & Contejean, SQLCoq/SQLCert, "A Coq mechanised formal semantics for realistic SQL queries" (CPP 2019)**
- An executable Coq semantics of select [distinct] / from / where / group by / having with NULLs, functions, aggregates, quantifiers and correlated subqueries — [dblp/CPP 2019](https://dblp.uni-trier.de/rec/conf/cpp/BenzakenC19.html); [preprint](https://easychair.org/publications/preprint/XGg9/open)
- The Standard's text on how aggregates collect their rows was "of no help", so they "proceeded by testing many queries over Postgresql and Oracle". Reaching the right set of tricky queries took "significant effort". **They used the real engines as the spec wherever the Standard was unclear** — [preprint](https://easychair.org/publications/preprint/XGg9/open)
- Random generator parameters included maximum nesting level, maximum relation instance size, maximum integer value and the proportion of NULLs. Queries were kept well-formed so that both engines would accept them — [preprint](https://easychair.org/publications/preprint/XGg9/open)
- Scale: 10,000 random queries. In all cases PostgreSQL 9.5.12, Oracle 18c (via LiveSQL) and SQLCoq gave the same results. For speed they ran the **OCaml code extracted from Coq**, not the Coq evaluator — [preprint](https://easychair.org/publications/preprint/XGg9/open)
- Discrepancies between the engines themselves: `select 1 from empty having 2=2` returns 1 in PostgreSQL and the empty set in Oracle. The model picked Oracle's behaviour for this case. **The model had to choose one engine's semantics** — [preprint](https://easychair.org/publications/preprint/XGg9/open)

**Ricciotti & Cheney, "A Formalization of SQL with Nulls" (Coq; arXiv 2020, J. Automated Reasoning 2022)**
- Formalizes NullSQL in Coq. It cites Guagliardo & Libkin's random-testing validation as its empirical grounding and mechanically re-derives their results instead of re-testing against engines — [arXiv 2003.11331](https://arxiv.org/pdf/2003.11331)

**TRAF, "Elucidating Type Conversions in SQL Engines" (ESOP 2025; Ye, Toro, Gutierrez, Oliveira, Tanter et al.)**
- A formal typing semantics that captures static and dynamic type behaviour through abstract operators. These operators are instantiated for PostgreSQL, MS SQL Server, MySQL, **SQLite** and Oracle — [Springer/ESOP 2025](https://link.springer.com/chapter/10.1007/978-3-031-91118-7_16)
- Validation: TRAF was implemented in Python for five engines and "tested with thousands of randomly-generated queries" — [Springer/ESOP 2025](https://link.springer.com/chapter/10.1007/978-3-031-91118-7_16) (summary from the search snippet; the full text was paywalled, so exact counts and discrepancies are unverified)

**KSQL (K framework, JAIST master's thesis)**
- An executable K semantics of core MySQL (create, select, insert, update, delete), developed by comparing detailed MySQL and Oracle 11 behaviour — [thesis PDF](https://www.jaist.ac.jp/~mizuhito/masterthesis/Pakakorn.pdf)

**Logos (Rocq, arXiv Aug 2026)**
- A mechanized, executable, PostgreSQL-oriented semantics used to certify SQL rewrites. It is evaluated on 389 rewrite pairs (Calcite, TPC-H/DS, WeTune). The abstract describes no differential validation against PostgreSQL — [arXiv 2608.15709](https://arxiv.org/abs/2608.15709)

**Lean**
- A search for a Lean 4 formalization of SQL or SQLite found no such project — [search results, no hits](https://www.researchgate.net/publication/353088178_The_Lean_4_Theorem_Prover_and_Programming_Language) (negative result; see Gaps)

### Inferences
- The accepted bar in the SQL-semantics literature is 10^4 to 10^5 random query+database pairs compared with bag equality (plus column names/order), with error outcomes treated as observable. A Lean SQLite model can adopt the same criterion. Because SQLite is dynamically typed, it should also compare `typeof()` of each result value (storage class), not only the value.
- The main recurring discrepancy in these projects was engine divergence from the Standard, not model bugs. For a model pinned to one engine (SQLite 3.51.0), SQLite itself is the ground truth, which is simpler than their situation. The SQLite documentation plays the role of "the Standard" and will sometimes be vaguer than the binary.
- Guagliardo & Libkin avoided types entirely (all-int schema) to make generation easy. For SQLite, type affinity is central to data preservation (e.g. TEXT '1' becoming INTEGER 1 under INTEGER affinity during INSERT...SELECT into a rebuilt table), so the generator must deliberately mix storage classes and declared types.
- SQLCert ran extracted code rather than evaluating inside the prover. The Lean equivalent is to compile the model with `lake build` and run the executable, not to rely on `decide`/`rfl` for bulk testing.

### Gaps
- No Lean 4 formalization of SQL or SQLite was found (GitHub, Zulip and arXiv searches returned nothing). Absence is not proof of non-existence.
- Could not obtain the TRAF full text: the exact number of random queries, which SQLite version was used, and what SQLite-specific discrepancies were found are unknown.
- Not researched in depth: HoTTSQL/Cosette (Chu et al., PLDI 2017) and Malecha et al. (POPL 2010, Ynot/Coq). To my knowledge neither validated a semantics against a running DBMS, but this was not verified.
- Found no mechanized formalization of SQLite-specific semantics (affinity, rowid, flexible typing) in a proof assistant.

## Q2. Executable spec + differential/conformance testing in industry and systems work (Cedar, ShardStore, SibylFS, WebAssembly, JSCert, Sail)

### Takeaway
The dominant proven pattern has four parts: (1) write the model as a readable executable program; (2) run it as an oracle against the real system on generated or conformance-suite inputs; (3) where the real system is nondeterministic or loosely specified, make the model return a set of allowed outcomes and check trace acceptance; (4) save the discovered cases as a regression corpus in CI. The scale ranges from a few thousand hand-curated tests (JSCert, Wasm) to tens of thousands of combinatorially generated scripts (SibylFS) to millions of fuzzed inputs per day (Cedar, ShardStore).

### Cited Findings

**AWS Cedar, Lean model + differential random testing (DRT) against Rust (FSE Companion 2024; OOPSLA 2024 language paper)**
- "Verification-guided development": an executable Lean model, Lean proofs, DRT to check that production Rust matches the model, and PBT for properties not yet proven or for components with no model (e.g. the parser) — [How We Built Cedar, arXiv 2407.01688](https://arxiv.org/pdf/2407.01688)
- DRT uses cargo-fuzz (libFuzzer, coverage-guided). Millions of requests, entities and policies are fed to both the Lean model and Rust, and any disagreement is a bug. With each Cedar version, a **minimized corpus is saved and run in CI** — [arXiv 2407.01688](https://arxiv.org/pdf/2407.01688)
- Generators: naïve independent generation produces mostly ill-typed policies and over-exercises error paths. They use **type-directed generation** (schema, then conforming entities, then policies and requests) plus a second generator that allows ill-typed conditions. Coverage guidance alone did not steer the second generator toward well-typed inputs, so they kept both — [arXiv 2407.01688](https://arxiv.org/pdf/2407.01688)
- Scale and cost: every target is fuzzed daily for 6 hours on 4 vCPU / 8 GB (ECS). Block coverage saturates by the end of the run — [arXiv 2407.01688](https://arxiv.org/pdf/2407.01688). The Lean model runs at about 5 µs per test case versus 7 µs for Rust — [Lean use case: Cedar](https://lean-lang.org/use-cases/cedar/)
- Bugs: proofs found 4 bugs in the validator (including a non-termination bug found while constructing the termination proof, which random testing missed). DRT and PBT found 21 bugs, by target: authorizer parity (ABAC type-directed) 6, validator parity 4, parser round-trip 6, formatter round-trip 2, validation soundness 3, RBAC parity 0, parser byte fuzzing 0 — [arXiv 2407.01688](https://arxiv.org/pdf/2407.01688)
- A DRT mismatch can expose a spec or design ambiguity rather than a bug on one side. A string-size operator was implemented differently in the model and in Rust (bytes vs codepoints vs graphemes), and the feature was dropped from the language — [arXiv 2407.01688](https://arxiv.org/pdf/2407.01688)
- Coverage lesson: "Complete line coverage alone does not guarantee effective testing." Even at full line coverage, 35.5% of generated conditions were boolean literals. A dedicated expression generator cut this to 9.7% — [arXiv 2407.01688](https://arxiv.org/pdf/2407.01688)
- Limitations: DRT cannot find bugs outside the generators' scope. AST-based generators never produced malformed syntax, so some parser bugs were missed — [arXiv 2407.01688](https://arxiv.org/pdf/2407.01688)
- Release gate: no Cedar version ships unless the model, proofs and differential tests are current — [AWS Open Source blog "Lean into verified software development"](https://aws.amazon.com/blogs/opensource/lean-into-verified-software-development/)
- The model, generators and DRT harness are public in `cedar-policy/cedar-spec` (directories cedar-lean, cedar-drt, cedar-policy-generators) — [cedar-spec README](https://github.com/cedar-policy/cedar-spec/blob/main/README.md)

**AWS S3 ShardStore, executable reference models + property-based conformance checking (SOSP 2021)**
- Each component has a reference model: an executable spec with the same interface but a much simpler implementation (e.g. the LSM-tree index is modeled as a hash map). The models are about 1% of implementation size, against a production system of over 40,000 lines of Rust — [ShardStore paper](https://www.cs.utexas.edu/~bornholt/papers/shardstore-sosp21.pdf)
- Conformance test: generate a sequence of operations from an enumerated alphabet (API operations plus background operations such as Reclaim and Reboot, which are no-ops in the model). Apply each to both the model and the implementation, compare results, and check invariants relating the two states after each step — [ShardStore paper](https://www.cs.utexas.edu/~bornholt/papers/shardstore-sosp21.pdf)
- Strict equality worked on the happy path, but equality of failures was "very difficult" to enforce. The model deliberately omits IO errors and resource exhaustion — [ShardStore paper](https://www.cs.utexas.edu/~bornholt/papers/shardstore-sosp21.pdf)
- **Argument bias**: Get prefers keys that were Put earlier, and sizes are biased toward page-size corner cases. Biases are probabilistic, so other cases still occur. Code coverage is monitored to judge how effective the tests are. Tens of millions of random sequences run before each deployment — [ShardStore paper](https://www.cs.utexas.edu/~bornholt/papers/shardstore-sosp21.pdf)
- Result: 16 issues prevented from reaching production, including crash-consistency and concurrency bugs. Engineers who are not formal-methods experts extended the models — [ShardStore paper](https://www.cs.utexas.edu/~bornholt/papers/shardstore-sosp21.pdf)
- They chose to write models in the implementation language so engineers keep them updated. Reusing the models as unit-test mocks keeps them in sync — [ShardStore paper](https://www.cs.utexas.edu/~bornholt/papers/shardstore-sosp21.pdf)

**SibylFS, POSIX/real-world file systems (SOSP 2015); the closest analogue: a stateful API, sequences of commands, observable results**
- The model is about 6,000 lines of higher-order logic in Lem, translated to HOL4 and Isabelle/HOL for proofs and to OCaml for an executable test oracle. It has variants for POSIX, Linux, OS X and FreeBSD — [SibylFS paper](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)
- **Oracle, not expected outputs**: "The fact that we have an executable test oracle greatly simplifies test suite development: we do not have to manually determine the intended outcome for each test, but rather can focus on generating tests with good coverage" — [SibylFS paper](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)
- Test suite: 21,070 automatically generated and hand-written scripts. They were run on more than 40 system configurations and produce about 46 MB of traces per run. Checking the whole suite takes about 79 s on 4 cores (about 266 traces/s), faster than executing the tests (152 s on tmpfs) — [SibylFS paper](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)
- Test generation used **equivalence partitioning / combinatorial testing** over hand-identified properties of paths and state (trailing slash, number of leading slashes, resolved type, empty/non-empty directory, same file via hard link, prefix relations, and so on). They generated at least one test per logically possible combination, and an OCaml checker mechanically verified that every possible combination had a test. rename alone got about 2,500 generated scripts, against about 50 in the OpenGroup POSIX suite. Sequential read/write behaviour was covered by hand-written tests — [SibylFS paper](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)
- **Nondeterminism**: the model maps (state, event) to a finite set of possible next states. When there are several allowed errors, the model enumerates all of them and the observed one selects the next state. Directory-listing order uses must/may entry sets. Concurrency is tracked via state sets. They "ruthlessly" controlled nondeterminism to avoid backtracking search. By comparison, Netsem's TCP trace checker needed a HOL constraint solver with backtracking and took about 2,500 CPU-hours for about 1,000 traces — [SibylFS paper](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)
- Results: on standard Linux (3.19, glibc, ext2/3/4), 21,061 of 21,070 traces were accepted. The 9 failures were artifacts of the chroot test harness, not file-system deviations. On other platforms the failures were mostly behaviours POSIX calls implementation-defined or unspecified. OS X had 34 failing traces, including a real integer-underflow bug in pwrite. Across configurations they found defects ranging from spec ambiguities to a storage leak (posixovl/VFAT) and an infinite busy loop (OpenZFS on OS X) — [SibylFS paper](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)
- Coverage: they measured **statement coverage of the model**, not of implementations, and reached 98%. Unreachable cases were kept as annotated lines to document exhaustiveness. They argue implementation coverage (libc + kernel + FS) is infeasible to measure across 40 configurations, and note the caveat that equivalence-partitioning assumptions may hide untested behaviour — [SibylFS paper](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)
- Process: a "virtuous circle". Testing on new platforms uncovered behaviours, which were added to the model along with new tests. A model-debugging tool shows the set of states tracked at each trace step. Checked traces render to HTML, and results from multiple platforms are merged with the differences highlighted — [SibylFS paper](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)

**JSCert / JSRef, ECMAScript 5 in Coq (POPL 2014)**
- Trust has two independent paths: (1) "eyeball closeness", where one line of ES5 pseudo-code corresponds to one or two JSCert rules and the Coq code is commented with the correspondences; (2) the reference interpreter JSRef, proven sound with respect to JSCert (about 3,500 lines of Coq proof), extracted to OCaml and run on test262 — [JSCert POPL paper](https://www.chargueraud.org/research/2013/js/jscert_popl.pdf)
- Scale: of 2,782 core-language test262 tests, JSRef passes 1,796. The rest fail because of features outside the model's scope (for-in, unspecified libraries, the parser), and JSRef passes every test expected to pass given its coverage. They measured coverage of the interpreter with OCaml bisect — [JSCert POPL paper](https://www.chargueraud.org/research/2013/js/jscert_popl.pdf)
- Discrepancy sources: bugs in JSCert/JSRef ("it was necessary to go around the loop many times"), bugs in all browsers, bugs in the ES5/ES6 standard, and bugs in test262 itself. Ambiguities were settled with the ECMA authors on es-discuss — [JSCert POPL paper](https://www.chargueraud.org/research/2013/js/jscert_popl.pdf)

**WebAssembly: WasmCert-Isabelle/Coq and SpecTec**
- The WasmCert-Isabelle extracted interpreter passes the official Wasm 1.0 test suite (about 17,810 tests) without error. At the time of the 2021 paper, end-to-end testing of the Coq-extracted interpreter was future work — [Watt et al., "Two Mechanisations of WebAssembly 1.0" (FM 2021)](https://conrad-watt.github.io/papers/watt2021.pdf)
- Mechanisation of the Wasm spec found bugs in the original specification, which were fixed before publication — [Watt et al. 2021](https://conrad-watt.github.io/papers/watt2021.pdf)
- SpecTec (PLDI 2024) is a single DSL source that generates LaTeX, prose and a meta-level interpreter. The interpreter ran all 49,833 applicable official Wasm 2.0 assertions (assert_return and assert_trap) in 58 s and passed 100%. Parsing/validation assertions were excluded because no backend existed for them. It also found 10 errors in 5 proposals (1,331 proposal tests) and would have prevented all in-scope historical spec bugs from the past two years — [SpecTec PLDI 2024](https://conrad-watt.github.io/papers/youn2024.pdf)
- SpecTec was adopted by the Wasm CG in 2025 — [webassembly.org news](https://webassembly.org/news/2025-03-27-spectec/)

**Sail ISA models**
- Sail generates executable emulators, spec coverage and automated instruction-sequence test generation from the same definition, plus Isabelle/HOL4/Coq definitions. The ARMv8-A model is translated from Arm's authoritative ASL. The models are complete enough to boot operating systems — [rems-project/sail](https://github.com/rems-project/sail); [Sail POPL 2019](https://www.cl.cam.ac.uk/~pes20/sail/sail-popl2019.pdf)
- About 7,000 litmus tests were used to keep operational and axiomatic RISC-V concurrency models in sync, and were run on SiFive FU540 hardware. Isla symbolic execution was used for automated ISA test generation for Arm Morello — [search summary citing Sail/Isla sources](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC11494631/)

### Inferences
- The SQLite problem fits the **ShardStore/SibylFS shape** (a stateful API driven by operation sequences, compared step by step) better than the Guagliardo shape (a single stateless query). A test is: start from an empty DB, apply a DDL/DML sequence, and after each step or at the end run observation queries: `SELECT *` with rowid, `typeof(col)`, `sqlite_schema`, `pragma table_info`, and `changes()`. The model predicts or accepts the observations.
- The user's plan (hand-written cases each proven in Lean by `decide`/`rfl`) is essentially JSCert's second path, and at small scale. The precedents suggest pairing it with (a) a compiled Lean executable run as an oracle over thousands of **generated** sequences, differentially against the `sqlite3` 3.51.0 binary, and (b) promoting interesting or failing generated cases into the proven suite (Cedar's minimized-corpus-in-CI practice).
- SQLite's documented nondeterminism (row order without ORDER BY, rowid choice after deletes or when max rowid is reached, error message text, which of several constraint violations is reported) calls for SibylFS-style handling. The model returns a set, or the checker normalises (bag comparison, allowed-error sets) rather than demanding exact equality.
- Generator design should follow Cedar: a schema-first, type-directed generator, plus a deliberately "ill-typed" or constraint-violating generator, because a naïve one mostly produces errors. Bias values toward type-affinity corner cases ('1', '1.0', ' 1', 1e20, blobs, NULL) and toward names that exist (the ShardStore argument-bias technique).
- Where a discrepancy lands in the SQLite documentation's gaps, the Cedar string-size episode and the SQLCert HAVING episode say to record the decision explicitly in the model, citing observed 3.51.0 behaviour.

### Gaps
- Netsem (TCP, HOL4) and x86-TSO validation numbers beyond what SibylFS quotes (about 1,000 traces, about 2,500 CPU-hours) were not independently researched.
- CompCert and CakeML semantics testing (e.g. Csmith against CompCert, CakeML test suites), P4K and eBPF semantics validation, and AWS Zelkova/Dafny were not researched within the tool budget.
- The OOPSLA 2024 Cedar language paper's own DRT numbers were not read. Figures come from the FSE 2024 companion paper and AWS/Lean pages; the AWS blog says "nearly two dozen bugs", consistent with 21 + 4.
- Current WasmCert-Coq test-suite status (post-2021) was not confirmed.

## Q3. Recurring lessons: executability, oracle vs trace acceptance, nondeterminism, coverage, and where discrepancies came from

### Takeaway
Five lessons recur. The model must be executable (and fast) to be validated at scale. Checking should be an oracle judgement ("is this observed outcome allowed?"), not handwritten expected outputs. Nondeterminism must be engineered out of the checking algorithm early. Coverage should be measured on the model itself, and line coverage alone is insufficient. Discrepancies come from every source (model bugs, implementation bugs, spec ambiguity, test-harness artifacts), so each mismatch needs triage.

### Cited Findings
- Executability as a validation requirement: "Providing an executable semantics allows one to be convinced that the semantics is correct as it can be confronted to real systems" — [SQLCert preprint](https://easychair.org/publications/preprint/XGg9/open). Guagliardo & Libkin's model existed in Python only for validation — [PVLDB 2017](http://www.vldb.org/pvldb/vol11/p27-guagliardo.pdf). Cedar's Lean model runs at Rust-like speed (5 µs vs 7 µs) — [lean-lang.org Cedar](https://lean-lang.org/use-cases/cedar/)
- An oracle frees test authors from writing expected outputs, so effort goes into coverage instead — [SibylFS](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)
- Trace acceptance with a set of allowed next states, enumerating allowed errors and resolving them by observation, versus the Netsem constraint-solving approach (2,500 CPU-hours for about 1,000 traces) — [SibylFS](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)
- Failure behaviour is the hardest to match exactly. ShardStore omitted most failures from its models — [ShardStore](https://www.cs.utexas.edu/~bornholt/papers/shardstore-sosp21.pdf). Guagliardo & Libkin did match error vs non-error outcomes — [PVLDB 2017](http://www.vldb.org/pvldb/vol11/p27-guagliardo.pdf)
- Coverage measures used: model statement coverage of 98% (SibylFS); interpreter coverage via bisect (JSCert); spec-derived coverage of the test suite (SpecTec's AL interpreter "allows us to easily analyze the coverage of the existing Wasm test suite"); implementation block coverage via libFuzzer (Cedar), with the caveat that it is insufficient on its own — [SibylFS](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf); [JSCert](https://www.chargueraud.org/research/2013/js/jscert_popl.pdf); [SpecTec](https://conrad-watt.github.io/papers/youn2024.pdf); [Cedar](https://arxiv.org/pdf/2407.01688)
- Discrepancy attribution:
  - SibylFS on Linux: 9 of 9 failures were test-harness (chroot) artifacts; elsewhere the failures were mostly spec looseness, plus real OS bugs — [SibylFS](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf)
  - JSCert: model bugs, browser bugs, standard bugs and test-suite bugs — [JSCert](https://www.chargueraud.org/research/2013/js/jscert_popl.pdf)
  - Cedar: mostly production bugs, but one led to a language-design change — [Cedar](https://arxiv.org/pdf/2407.01688)
  - SQL work: zero final mismatches, but only after the model was adjusted per engine; engine-versus-engine differences were the main finding — [PVLDB 2017](http://www.vldb.org/pvldb/vol11/p27-guagliardo.pdf); [SQLCert](https://easychair.org/publications/preprint/XGg9/open)
- Proofs and tests catch different bugs. Cedar's non-termination bug was found only by the proof, and random testing's probability of triggering it was "extremely low". Validation-soundness bugs were found by PBT before the proof was complete — [Cedar](https://arxiv.org/pdf/2407.01688)
- Model and tests co-evolve in a loop (SibylFS "virtuous circle"; JSCert "go around the loop many times") — [SibylFS](https://www.cl.cam.ac.uk/~pes20/SOSP15-paper102-submitted.pdf); [JSCert](https://www.chargueraud.org/research/2013/js/jscert_popl.pdf)

### Inferences
- For the Lean SQLite model: keep the model computable. Avoid `noncomputable`, `Classical.choice` and `Prop`-only definitions in the core semantics; put any relational or nondeterministic spec behind an executable "allowed outcomes" function, so the same definitions serve proofs, `decide` on small cases, and a compiled oracle binary.
- Measure coverage on the Lean model. There is no off-the-shelf Lean line-coverage tool I could confirm, so a practical proxy is to instrument or tag each semantic clause, or to count which statement/constraint/affinity branches the corpus exercises. Separately, the `sqlite3` binary can be built with gcov to report which parts of sqlite3.c the corpus reaches. That is feasible for SQLite, unlike SibylFS's multi-component stack, because SQLite is a single C file.
- Keep a mismatch log that classifies each discrepancy as model bug, harness/normalisation bug, SQLite doc ambiguity, or genuine SQLite behaviour worth noting.

### Gaps
- No precedent was found that quantifies the ratio of model bugs to implementation bugs across a whole project. Only the qualitative lists above are available.
- Found no data on Lean-specific code coverage tooling (not searched in depth).

## Q4. Spec-traceability: linking model definitions to spec text

### Takeaway
The main traceability technique is structural "eyeball closeness": each clause of the spec corresponds to one or two definitions or rules, annotated in comments, so a domain expert can audit the model side by side with the prose. SpecTec goes further and generates the prose from the formal source. For SQLite, the natural anchor is its R-requirement IDs, though no precedent specifically linking a formal model to SQLite R-IDs was found.

### Cited Findings
- JSCert: "Every line of pseudocode in ES5 corresponds to one or two rules in JSCert, and our code is commented to make these correspondences explicit". They deliberately made implicit state, exceptions and divergence explicit to aid the audit, and aimed for the model to be "close enough to ES5 that (at least several) ECMA authors should be able to proof read our definitions" — [JSCert](https://www.chargueraud.org/research/2013/js/jscert_popl.pdf)
- WasmCert-Isabelle/Coq closely follow the whole Wasm 1.0 semantics "directly, as stated in the standard", which is feasible because the standard is compact — [Watt et al. 2021](https://conrad-watt.github.io/papers/watt2021.pdf)
- SpecTec: a single source generates the formal notation, the prose pseudocode and the interpreter, so the spec document and the executable semantics cannot drift apart. It would have prevented 7 historical "prose errors" and 3 type errors — [SpecTec PLDI 2024](https://conrad-watt.github.io/papers/youn2024.pdf)
- Sail can "show specification coverage" from the same definitions used for emulation and proof — [rems-project/sail](https://github.com/rems-project/sail)
- Cedar ties releases to the model: no release unless the model, proofs and DRT are current — [AWS blog](https://aws.amazon.com/blogs/opensource/lean-into-verified-software-development/)

### Inferences
- Tag each Lean semantic definition or branch with the SQLite doc URL and R-requirement ID (e.g. in docstrings), and tag each proven test case with the R-IDs it exercises. This gives a clause-coverage matrix analogous to SibylFS model coverage, plus a JSCert-style audit path. It also fits the workspace rule that docstrings link to specs.
- Where SQLite's docs are silent, cite the observed 3.51.0 behaviour (the test case ID) as the "spec" for that branch. This mirrors how SQLCert used PostgreSQL/Oracle when the Standard was unhelpful.

### Gaps
- Found no published formal model that is traced to SQLite's R-requirement identifiers.
- Did not verify how Cedar's written language spec is cross-referenced to specific Lean definitions (only the release-gating policy was confirmed).
