## Outcome

1. **Forms.** `INSERT OR ABORT | FAIL | IGNORE | REPLACE | ROLLBACK INTO t ... VALUES ...`,
   with or without `ON CONFLICT` clauses and `RETURNING`, and `REPLACE INTO` (SQLite's
   name for `INSERT OR REPLACE`). In `CREATE TABLE` of the schema, the clause
   `ON CONFLICT algorithm` of a `PRIMARY KEY`, `UNIQUE` or `NOT NULL` column or table
   constraint. `UPDATE OR` stays refused (Amendment 4, "Out of scope").
2. **Algorithm of a failure.** A key or NOT NULL failure of a row uses the algorithm of
   the statement's `OR` clause, or else the algorithm of the failing constraint, or else
   ABORT (R-33948-22286). A conflict on the target of an UPSERT clause is handled by that
   clause first. `datatype mismatch` of a rowid alias is never ignored or replaced: it is
   the statement's error under every algorithm (checked natively).
3. **ABORT** is the behavior of today: the statement fails and the database is as before
   it.
4. **FAIL** stops at the failing row with the error and keeps the changes of the earlier
   rows of the statement (R-31882-08811), which also count in `changes()`.
5. **IGNORE** skips each row that fails a key or NOT NULL (R-50299-05307); the statement
   succeeds, and the skipped rows are not counted or returned.
6. **REPLACE** deletes, before it inserts the row, every existing row that the row
   conflicts with on any key (R-54702-17780); the deleted rows are not counted
   (R-37019-57602). A NULL in a NOT NULL column takes the column's default, or is ABORT
   without one (R-12527-00403). `RETURNING` returns the inserted rows.
7. **ROLLBACK** fails the statement and rolls back the open transaction, which then is no
   longer open (R-31881-13880; a later `COMMIT` is `cannot commit - no transaction is
   active`); without a transaction it is ABORT (R-42089-41020).
8. **Restrictions and fixed behavior** (checked natively):
   - A rowid alias `datatype mismatch` is ABORT under every algorithm, also under FAIL.
   - The row of `DO UPDATE` is checked with ABORT, whatever the `OR` clause or the
     constraint algorithms say.
   - When the keys of a row's checks have different algorithms other than REPLACE (only
     possible through constraint algorithms), SQLite's internal order of keys decides
     which applies: a model restriction `mixed-conflict-algorithms`.
   - UPDATE of a table with a constraint algorithm other than ABORT is a model
     restriction `constraint-algorithm-update`, as `UPDATE OR` is out of scope.
   - REPLACE of a NULL in a NOT NULL column with a `CURRENT_TIMESTAMP` default is the
     time-value restriction.
9. **Laws.** `statement_atomicity` keeps its statement for every failure except a FAIL
   failure and a ROLLBACK failure; a new law states that a ROLLBACK failure leaves the
   database of the transaction snapshot, also as the persisted database.
10. **Verification target.** `Contract.lean` does not change; every write keeps
   `Conforms`. A statement without `OR` clause and without constraint algorithms keeps
   its current semantics.
11. **Evidence.** Authored coverage cases agree with native SQLite 3.51.0 and have kernel
   proofs; each mutant below changes a verdict; the verdict counts of the claimed corpora
   do not go down.

## Tests

- Lean examples: each algorithm on a key failure and on a NOT NULL failure; FAIL with
  earlier rows; REPLACE of two conflicting rows; ROLLBACK inside and outside a
  transaction; a constraint algorithm and an `OR` clause that overrides it; an UPSERT
  target before the algorithm.
- Proofs: every INSERT keeps `Conforms` under every algorithm; ABORT has the semantics of
  today; the law that a failed statement keeps the database holds for every algorithm
  except FAIL, which keeps the earlier rows.
- Authored coverage cases (native SQLite as the oracle): each item of the outcome,
  `REPLACE INTO`, each algorithm inside a transaction, the change count and `RETURNING`
  of each algorithm, a mismatch under IGNORE and REPLACE, each constraint algorithm and
  its precedence, and an UPSERT with an `OR` clause.
- Mutants, each changing the verdict of an authored case: `OR FAIL` that keeps no row;
  `OR IGNORE` that stops at the row; `OR REPLACE` that deletes only one conflicting row;
  deleted rows counted in `changes()`; ROLLBACK that keeps the transaction open; the
  constraint algorithm ignored; the `OR` clause that does not override the constraint
  algorithm.

## Key points for the implementer

- **Frontend.** `belay/sqlite/syntax_writes.py` `insert` refuses `orconf`; the column and
  table constraints of `CREATE TABLE` (`syntax_definitions`) refuse `onconf`. `REPLACE
  INTO` is the `insert_cmd ::= REPLACE` production of `parser/upstream/parse.y`.
- **Atomicity laws.** `Laws.lean` (`literal_cases`, `statement_atomicity`) and the
  conformance outputs assume that a failed write keeps the database. FAIL breaks that:
  its failure carries the database after the earlier rows. Decide how `Outcome.failure`
  and the laws state this without weakening ABORT.
- **Transactions.** ROLLBACK needs the snapshot of `SqlState` (`SqlExecution.advance`);
  today only `ROLLBACK` statements restore it.
- **Order of checks.** SQLite checks NOT NULL first, then the keys; it checks REPLACE
  keys after the other keys, so a row that conflicts on an ABORT key and a REPLACE key
  fails without deleting. Check each order natively before modeling it, and restrict
  mixed algorithms whose order the model does not decide.
- **Defaults.** The model admits no constant default in a write (only
  `CURRENT_TIMESTAMP`, a time restriction), so REPLACE of a NULL in a NOT NULL column is
  ABORT or the time restriction.
- **UPSERT.** `Upsert.lean` (`upsertRow`, `checkedRow`) is the per-row execution that the
  algorithms extend; the plain INSERT path (`insertOutcome`) is ABORT only.
- **Kernel and mutant cost.** Keep authored cases small; measure the mutant and model
  suites after the change.
