## Owner decisions

Decided on 2026-10-23: the owner accepted the recommendation of each decision below.
ADR 0019 D2 and the deferred row of ADR 0017 are amended to match (decisions 1, 3 and 4).
The corpus of this slice is corpus-v50 (slice 3 records corpus-v49).

1. **The order of the tables in the forms without a table name.** D2 says "in SQLite's order".
   SQLite walks its schema hash table. With at most three tables the order is newest first.
   From the fifth hash entry (`sqlite_schema` counts) the order follows the hash of the names
   and the size of the bucket array, which `sqlite3MallocSize` sets. A DROP does not remove
   the buckets, so the order depends on the history of the connection. Checked: `p`, `c1`, `c2`
   give `c2 c1`, and with `c3` they give `c3 c1 c2`. The judge compares `PRAGMA` rows as a bag,
   so the corpora do not see the order. The order matters for a row limit, for the first
   `foreign key mismatch` error, and for claims about the output.
   **Recommendation:** the model gives exact rows when at most one table gives rows or errors.
   When two or more tables give rows (or have a mismatch), the output is `Output.unmodeled`.
   Amend D2 to say so. Alternatives: `Output.oneOf` over the orders of the tables' blocks
   (exact, but n! results, and a limit cuts each one); or a port of `hash.c` (rejected: it
   copies allocator and reload details of SQLite that the model has no other use for).
2. **The evidence for failing checks.** No modeled statement reaches a database whose NOT NULL,
   CHECK, `STRICT` or unique constraints fail (ADR 0022, D5: such a run is a finding), and the
   recorder refuses `writable_schema` and `ignore_check_constraints`. So no corpus case can
   show a failure row of `integrity_check` or `quick_check`; the corpora show only `ok`.
   **Recommendation:** Lean examples with kernel proofs over databases built in Lean, with the
   native probes in the task file and in this file as their reference. Alternative: model
   `PRAGMA ignore_check_constraints`, so that a corpus reaches CHECK failures (outside D2, and
   ADR 0022 leaves it open).
3. **The evidence for `recursive_triggers` on.** The recorder accepts a setting statement only
   at the profile's value and reads the settings back after the script
   (`execution_profile.py:79-95`), so a corpus case cannot change the setting. The model
   refuses a profile with the setting on (`profile_scope.py:28-35`).
   **Recommendation:** the model starts from the profile's setting, `profile_scope.py` accepts
   such a profile, and the authored corpus gets a profile `recursive-triggers` (in
   `authored_cases.py`). A change of the setting inside a script gets Lean examples only.
4. **The text of D2 and of ADR 0017.** SQLite's `integrity_check` also checks the stored form of
   each cell of a table that is not `STRICT`, and the key order of a `WITHOUT ROWID` table.
   Under `Database.Admitted` the first never fails (`Table.RowsStored`), and the second fails
   only with `KeysUnique`, so the laws of D2 stay true. ADR 0017's deferred row names
   "`pragma_table_info` and the other table-valued pragma functions"; D2 names only
   `pragma_table_info` and `pragma_foreign_key_list`, and no corpus case uses another one.
   **Recommendation:** keep the scope of D2; amend D2 with these facts and with decision 1, and
   amend the row of ADR 0017 to the two functions of D2.

## Native probes (3.51.0, the dev shell's `sqlite3`)

- Broken databases come from `writable_schema` after `.dbconfig defensive off`, reopened.
  Tables `t(a NOT NULL, b CHECK (b > 0), c, d INTEGER PRIMARY KEY)` with `CREATE UNIQUE INDEX
  tc ON t(c)`, rows `(NULL,-1,'u',1)`, `(NULL,5,'u',2)`, `(3,-2,'v',3)`: `NULL value in t.a`,
  `CHECK constraint failed in t`, `non-unique entry in index tc`, `NULL value in t.a`,
  `CHECK constraint failed in t`. `quick_check` gives the same without the index row.
- `STRICT` `s(x INTEGER NOT NULL, y TEXT NOT NULL, z INT, q INTEGER, r REAL)` with
  `(NULL,1,'a',2.5,'z')` and `(1,'x',2,3,X'00')`: `NULL value in s.x`, `non-TEXT value in s.y`,
  `non-INT value in s.z`, `non-INTEGER value in s.q`, `non-REAL value in s.r`, `non-REAL value in
  s.r`.
- Unique indexes `uk(k, v)`, `un(v COLLATE NOCASE)`, `ui(k) WHERE f > 0` (created ui, un, uk)
  over `(1,'A',1)`, `(1,'a',1)`, `(1,NULL,0)`, `(2,NULL,1)`, `(2,NULL,1)`: `un`, `ui` (row 1),
  `ui` (row 4).
- `WITHOUT ROWID` `w(k, v, PRIMARY KEY (k))` over `(1,1)`, `(1,2)`, `(1,3)`, `(2,1)`: two rows
  `row not in PRIMARY KEY order for w`; `quick_check` gives `ok`.
- The limit and the value forms of task outcome 1, and `PRAGMA integrity_check(nosuch)`:
  `no such table: nosuch` at prepare.
- `foreign_key_check` over `c(x REFERENCES p, y REFERENCES p(k), z REFERENCES p(n))`: rows by
  rowid, then `fkid`; `fkid` 0 is the last declared key; the setting `foreign_keys` is off.
- `PRAGMA recursive_triggers = 1` inside `BEGIN` takes effect; `= 2` and `= 'yes'` give 1,
  `= 'abc'` gives 0. With the setting on, `INSERT OR REPLACE` fires the DELETE trigger.
- With `recursive_triggers` on, the body statements of the DELETE trigger of a row that REPLACE
  deletes run with REPLACE: a duplicate key that such a body inserts replaces the old row
  (`sqlite3GenerateConstraintChecks` gives `OE_Replace` to `sqlite3GenerateRowDelete`).
- SQLite counts the frame of a trigger program when it starts the program, before the `WHEN`
  condition: under `.limit trigger_depth 3`, a chain whose program at depth 4 has a false
  condition fails with `too many levels of trigger recursion`, and a chain of 3 rows succeeds.
