## Owner decisions

Each recommendation is the option that the task file assumes.

Decided on 2026-10-24: the owner accepted every recommendation. 1 a), 2 c), 3 a), 4 b) (the
check of `Run.checked`, its else branch and `invalidReason` go once slice 4 lands), 5 a), 6 a)
for `uniqueEmail_ok` (the Lean precondition) and the SQL precondition through
`pragma_table_info` for `balance_ok`, and 7 a) (three parts).

1. **Where the lemma library ends in S4.** The guide's library has query, effect, frame,
   specification, footprint and program lemmas.
   - a) S4 gives the query lemmas, the expression laws, the schema facts, the success lemmas
     that level 2 reads, and the program laws. Effect, frame, specification and footprint
     lemmas come with S6, the first reader.
   - b) S4 also gives the effect and frame lemmas (`rows_insert`, `rows_frame`, …).
   Recommendation: a). No example of "Queries as propositions" or "Level 2" reads the rows
   after a write, so b) is work with no reader in S4 (review condition R18).
2. **What "every environment" means in `succeeds`.** The guide says "every environment".
   `Env.default` has no clock and knows no counter, so a script that reads either ends at
   `Output.unmodeled` under it.
   - a) Every `Env`, with `Output.unmodeled` not a success: a script that reads the clock or a
     counter can never succeed.
   - b) Every `Env`, and only `Output.error` is a failure. This holds for a run that the model
     cannot continue, and so approximates (ADR 0017, D4).
   - c) Every complete `Env` (a clock, and all three counters known, at any values). A real
     connection has all of them; `Env.default` is the absence of knowledge, not an environment.
     `Script.run_env` shows that for a script that reads neither, this is the default run.
   Recommendation: c). It keeps D4, and it lets a script with `CURRENT_TIMESTAMP` succeed.
3. **`Succeeds` for a program with a branch.** A program reads the first result of an
   `Output.oneOf` (S3, decision 3), so `db.run` follows one branch.
   - a) `Succeeds` follows every result of every `Output.oneOf`, by a short recursion over
     `Sql α`. The guide says "this covers every branch that it can take".
   - b) S4 defines `Succeeds` for scripts only; programs wait for S6's `WP` instance (guide open
     question 12).
   Recommendation: a). The test with a `LIMIT 1` tie shows the difference from `db.run`. S6 then
   proves the equation with the triple.
4. **The check in `Run.checked`.** ADR 0022 slice 4 proves that a run keeps `Database.Valid`.
   - a) Keep the decision at the end of each run, and add a theorem that its else branch never
     happens.
   - b) Remove the decision, the else branch, `invalidReason` and the outputs that it adds; the
     run gives its `Database` from the theorem. The project rule is to delete replaced code
     (`CLAUDE.md`, "Replaced code"). The kernel proofs of concrete runs get cheaper. If a later
     statement bypasses a constraint, its task decides (ADR 0022, D5).
   Recommendation: b), after slice 4 lands.
5. **Automation.** The guide has `sql_auto`, `sql_simp`, `sql_run`, `sql_commute`.
   - a) S4 gives `sql_simp` as a simp attribute set, with `grind` attributes where they work. No
     tactic of its own, and no `sql_auto`.
   - b) S4 also gives `sql_auto` = `sql_simp`, then `grind`, with the "Try this" suggestion.
   Recommendation: a). `sql_auto` of the guide first tries `sql_commute` and `sql_run` (S6), so
   a version now would change when S6 lands. Proofs in S4 are written by hand with `simp`. The
   guide's `by sql_auto` becomes a written proof until S6.
6. **The guide's two claims that are false over every database.** Checked with the dev shell's
   `sqlite3` 3.51.0 (see "Findings"). Corrected forms:
   - `uniqueEmail_ok`: a) `Succeeds uniqueEmail (fun db => Holds G db ∧ db.catalog.find
     (Identifier.ofString "customers_email") = none)`, and the guide says that the model cannot
     read index names in SQL. b) Add `pragma_index_list` to the model (ADR 0019 slice, so SQL can
     state it). c) A claim about one concrete database.
   - `balance_ok`: add to the SQL precondition that `ledger` has the columns `account` and
     `cents`, and that the declared type of `cents` is `INTEGER`, with `pragma_table_info`.
   Recommendation: a) for the first, and the SQL precondition for the second. The Lean predicate
   of `Succeeds` (workspace rule 19) is why a) costs nothing in the primitive.
7. **The split.**
   - a) Three parts, each with its own `just test-full` and `just verdict`: part 1, outcomes 1
     to 6 (claims over every database, no dependency on ADR 0022 slice 4); part 2, outcomes 7
     to 9 and 11 (level 2), after the corollary of slice 4 lands (`Succeeds` needs it); part 3,

   Recommendation: a). Part 1 can start now. Parts 2 and 3 wait for slice 4 (outcome 7 needs its corollary); part 3 is small.

## Findings

Measured on 2026-10-24 on this tree (`just dev-build`, Lean 4.34.1, native SQLite 3.51.0). A
local result is not evidence (`CLAUDE.md`); each native claim is also a case or a kernel example
that the tests of the task file hold.

- **The guide's `uniqueEmail_ok` is false over every database.** `CREATE UNIQUE INDEX
  customers_email ON customers (email COLLATE NOCASE)` fails with `index customers_email already
  exists` when an index of that name exists, and with `there is already a table named …` when a
  table does, also with `IF NOT EXISTS`. The condition of the guide does not exclude either.
  The model agrees: `resolveCreateIndex` gives `.indexExists` and `.tableNameUsed`. Two NULL
  emails make the condition false (`GROUP BY` groups NULLs), which is safe.
- **The guide's `balance_ok` is false over every database.** A `ledger(cents)` without
  `account` fails with `no such column: account`. A `ledger(account, cents TEXT)` with eleven
  rows `'0999999999999999999'` passes the condition (compared as text, each value is between the
  bounds) and `sum(cents)` fails with `integer overflow` (`sum` reads the text as an integer).
  With `cents INTEGER`, the same rows are stored as 999999999999999999 and the condition fails.
- **The guide's lemma `holds_where` omits faults.** `SELECT 1 FROM t WHERE abs(x) = 1` over
  rows `1` and `-9223372036854775808` returns a row and then fails with `integer overflow`. The
  model gives `Output.unmodeled` for it, so the lemma needs a no-fault condition.
- **Proofs over a free `db` cannot use `decide`.** `decide +kernel` gives `Expected type must not
  contain free variables`. `rfl` proves `Holds (sql r"SELECT 1") db` and fails for `SELECT 1
  WHERE 1 = 1` with `maximum recursion depth has been reached`. After `unfold Fails
  Script.outputOn Database.Raw.run Script.runOn`, the goal is the `match` on `resolveStatement`
  of the task file's "Key points".
- **The concrete forms resolve in the model today.** On a concrete database, `decide +kernel`
  proves `Holds` for `pragma_table_info … WHERE name = 'amount'`, for `NOT EXISTS (SELECT 1 …)`
  and for `(SELECT count(*) …) = 2`. `GROUP BY email COLLATE NOCASE HAVING count(*) > 1` and
  `NOT BETWEEN` resolve. The `CREATE UNIQUE INDEX` gives `[error 19]` on the guide's duplicate
  emails, and the `sum` query gives `[error 1]` on two rows of 4611686018427387904 cents. `$n`
  needs a Lean variable `n`; `:n` makes it an argument (S3).
- **Native evidence exists for each rule that S4 proves about.** Cases of the frozen corpora
  (searched in `migrationSql` and in the traces of all shards, 2026-10-24): `CREATE UNIQUE INDEX`
  failing on duplicates (corpus-v29 `index-runs-unique-duplicates`, corpus-v5 `index3-1.2`),
  `index … already exists` (corpus-v5 `index-6.1`), `COLLATE NOCASE` in an index term (corpus-v31
  `collate-index-term`), `GROUP BY … COLLATE NOCASE` (corpus-v31 `collate-group-by`),
  `HAVING count(*)` (corpus-v44 `group-having`), `NOT BETWEEN` (corpus-v43 `form-between`),
  `pragma_table_info` (corpus-v50 `table-info-function`), `EXCEPT` (corpus-v49 `compound-except`)
  and `sum` overflow (corpus-v8 `sum-overflow`). `CREATE INDEX IF NOT EXISTS` appears in 92
  cases (for example corpus-v5 `index6-14.1`). Whether one of them covers a clash with a table
  name was not checked. The task needs no new case, because S4 adds no model behavior.
- **ADR 0022 slice 4 is not on `main`.** Its workspace has the CHECK lemma commits only. Its
  decision 5 became a) on 2026-10-24 (repeated key columns are modeled), and its task file may
  still say b). S4 reads the corollary for `runScriptFrom` and the surface form for
  `Sql.runFrom` (its decision 6, a)); outcomes 1 to 6 do not need them; outcomes 7, 8 and 10 do, and so do
  the examples of outcome 11 that use `Succeeds`.
