## Outcome

1. **Form.** `json_each(json [, path])` as a source of `FROM`, with an optional alias
   (default name `json_each`, in any case): alone, after tables or other `json_each`
   sources in a comma list, and as the right side of an inner `JOIN` with an optional `ON`
   condition. Its arguments may read the columns of the sources before it; SQLite then
   evaluates it once for each row of those sources (the nested loop).
2. **Rows.** One row per element of the array or member of the object at the path, in
   document order with duplicate keys kept; one row for a scalar; no row for a NULL
   argument or a path that selects nothing. The visible columns, which `*` shows, are
   `key`, `value`, `type`, `atom`, `id`, `parent`, `fullkey` and `path`; the hidden columns
   `json` and `root` can be named. Each column is as SQLite gives it (checked natively):
   for example `key` is the index or the label, `atom` NULL for a container, `parent`
   NULL, and `id` the node's byte position in SQLite's JSONB encoding of the whole document
   (1, 4 and 9 for `[10,{"x":1},30]`).
3. **Names.** A column name of `json_each` resolves like a table column: an unqualified
   name that two sources have is `ambiguous column name: %s`; `json_each.key` and an alias
   qualify it.
4. **Restrictions (model restrictions with registry entries).** A `LEFT`, `RIGHT` or
   `FULL` join with `json_each`, `USING` with `json_each`, an argument that reads a source
   after the `json_each`, a schema-qualified `json_each`, `json_tree` and every other
   table-valued function stay refused.
5. **Errors.** Too many arguments is SQLite's prepare error
   `too many arguments on json_each() - max 2`. A JSON failure of `json_each` (malformed
   JSON, a bad path) is reported by SQLite only when it scans the source for a row, so
   the model does not describe it: a statement in which a `json_each` may fail over its
   source rows is unsupported for that data, as for the other JSON failures of slice 6b.
6. **Verification target.** `Contract.lean` does not change; every write keeps
   `Conforms`. Queries without `json_each` keep their current semantics.
7. **Evidence.** Authored coverage cases agree with native SQLite 3.51.0 and have kernel
   proofs; each mutant below changes a verdict; the verdict counts of the claimed corpora
   do not go down.

## Tests

- Lean examples: the rows of arrays, objects, scalars, nested containers, a path and a
  missing path, with each column; the node positions for headers of each size.
- Proofs: the join laws of `QueryJoinLaws.lean` that hold today keep holding for queries
  without `json_each`.
- Authored coverage cases (native SQLite as the oracle): `json_each` alone, after a table
  with a correlated argument, as an inner join with `ON`, twice with aliases; `*`, the
  hidden columns, qualified and ambiguous names; `WHERE`, `ORDER BY`, aggregates and
  `GROUP BY` over its columns; a NULL argument; the prepare error of too many arguments.
  The upstream `json101`, `json102` and `json104` cases with `json_each` that agree are
  the second check.
- Mutants, each changing the verdict of an authored case: `id` as the element index;
  `key` of an array as text; `atom` of a container as its JSON text; the `id` of an
  object member at its value instead of its label (the order of the rows of a query
  without `ORDER BY` is not observable); `json_each` not re-evaluated for each left row; the hidden
  columns shown by `*`.

## Key points for the implementer

- **Model shape.** Today the first source is a table (`Query.table`) and each join has a
  table (`Resolved.Join.table`). A `json_each` source is a function of the joined row
  before it. A query whose first source is `json_each` can be read as the one empty row
  of a query without `FROM`, joined with the function; but `Query.mustFail` and
  `Query.source` decide "no `FROM`" by `table.isNone` today, and that must stay exact.
- **Join laws.** `QueryJoinLaws.lean` proves facts over joins of tables; keep each law
  for the queries it covers today, and state its premises exactly when they change.
- **Rows port.** `id` follows `jsonTranslateTextToBlob` and `jsonBlobChangePayloadSize`
  (header sizes by payload size); `fullkey` and `path` quote labels that are not
  alphanumeric (`$."a b"`). Check each column natively, building inputs with
  `CAST(X'..' AS TEXT)` (the sqlite3 shell converts `\uXXXX` in its input).
- **Frontend.** `syntax_sources.from_clause` refuses table-valued functions today; the
  parser production of a function in `FROM` has its arguments as an `exprlist`.
- **Failures.** The rules of `JsonFaults.lean` and `JsonReady.lean` evaluate expressions
  over rows; a `json_each` adds a failure that depends on the left row, not on a result
  row. Natively, `SELECT 1 FROM t, json_each('{bad')` over an empty `t`, and the same with
  `WHERE 0` or `LIMIT 0`, does not fail.
- **Cost.** Keep authored cases small (kernel proofs of the rows) and measure `tests.model`.
