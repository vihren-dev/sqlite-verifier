## Scope

A user writes scripts with `$x` and `:name`, writes programs in `do` notation with `send`,
`query` and `single`, runs them with `db.run`, reads the result as a `Run`, and gives a run
a clock with `Env`. The guide is the target; where it differs from an ADR decision or from the
model, the ADR and the model apply, and the guide changes (a local commit of the product
repository, as in S2).

Out of scope:

- `withTransaction`: the guide uses a savepoint inside an open transaction, and the model has
  no `SAVEPOINT` (`Syntax.Statement` has `begin`, `commit` and `rollback` only). Owner decision
  1 of the status file.
- The other inputs of the guide's `Env`: random values, the connection state
  (`changes()`, `last_insert_rowid()`) and the choice of profile. The first two wait for a
  model ADR (ADR 0017, "Deferred, with their triggers"). The runs keep `Profile.pinned`.
- `$name` and other parameters in `.sql` files (S7), the monad laws and the other program
  lemmas (S4, the lemma library), triples and `Native` (S6), and the editor's hovers of
  parameters.

## Outcome

1. **`$x` is a Lean variable.** In `sql r"..."` and `sql! db r"..."`, a parameter `$x` is the
   Lean term `x`, elaborated where the script is, and coerced to `Value`. The statement gets
   the value of `x` at the number that SQLite gives `$x` (ADR 0019, D1). The surface gives
   the coercions that the guide uses: `Value`, `String` (exists) and `Int64` (new, the INTEGER
   of `Int64.toInt`). When `x` does not resolve, or its type has no coercion to `Value`, the
   error is at `$x` in the SQL text. A `$` name that is not a Lean identifier, such as
   `$a::b` or `$a(x)`, is an error at the parameter that says to write a Lean identifier.
2. **Every other parameter makes the script a function.** `?`, `?NNN`, `:name`, `@name` and
   `#name` each give one argument of type `Value`. A name gives the argument of that name
   without its sign; `?` and `?NNN` give `p` and the number that SQLite gives them (`?5` gives
   `p5`). One parameter gives one argument for the whole script, however often it appears and
   in however many statements; each statement binds the argument at its own number. The
   arguments are explicit, in the order of their first appearance in the text, so
   `setAmount (id := 1) (amount := 15)` works. Two parameters that give one argument name, such
   as `:id` and `@id`, or `:id` and `$id`, are an error at the second one that says to rename
   one. A number holds one value, so two parameters of one statement that get one number from
   SQLite must give one argument (`?` and `?1` give `p1`): `$x` and `?1`, or `:a` and `?1`, as
   the first two parameters are an error at the second one. A script without parameters is a
   `Script`, as in S2.
3. **The term is built on the primitive.** The script of a function is
   `Script.withValues` of the script without values, so `Script.withValues` stays the way to
   bind values that the notation cannot express, and `sql! db r"..."` and `sql r"..."` stay
   equal by `rfl`. Each statement's list has one item for each number up to its largest one;
   a number without a parameter in the text is NULL, as SQLite binds it.
4. **`db!` and parameters.** A parameter in the text of `db!` is an error at the parameter,
   because a database literal has no arguments (owner decision 5). Today `db!` runs each
   statement with no values, so a parameter is NULL without a message.
5. **Programs.** `Sql α` is an inductive type with two constructors, `Sql.pure` and
   `Sql.exec`: one statement with its values, and the function that receives its `Output`
   and gives the rest of the program. A `Monad` instance gives `do` notation. Over these:
   - `send s : Sql (List Output)` sends each statement of `s`; the value is their outputs.
   - `query s : Sql (Except Nat (List (List Value)))` sends a script of one statement; the
     value is its rows, `.ok []` for a statement without rows, or `.error code`.
   - `single s : Sql (Option Value)` sends a script of one statement; the value is
     `some v` when the statement gives exactly one row of one column, and `none` for no row,
     for more rows or columns, and for an error.
   - For `Output.oneOf`, `query` and `single` read the first result (`compareResults` order),
     so a run of a program is one run that SQLite permits, as the guide's "Programs see one
     order" says (owner decision 3).
   - `query` and `single` take a script of exactly one statement of any form, so that
     `INSERT ... RETURNING` gives its rows (owner decision 4). The argument is checked where
     the script is written, also for a script with `$x` values.
   - A `Script` on its own line in a `do` block is sent and its value is dropped.
   - `List.allOk` of outputs: no output is `Output.error` or `Output.unmodeled`.
6. **Runs of programs.** `Sql.run p db` is the interpreter, and `Database.run db p` is the
   same run with the database first; both take `(env := e)` as a named argument after the
   program, with `Env.default` when it is not given. `db.run` takes a `Script` and a program
   (guide open question 15, owner decision 2); a script is the program `send s`. `Run α` has
   `value`, `outputs`, `db`, `start`, and S2's `transaction` and `foreignKeys`. Each statement
   runs as one statement of S2's run (`runScriptStep`), at the next index, on the connection
   that the earlier statements left. A statement whose output is `Output.unmodeled` ends the
   program: its outputs end with that output, the program's continuation does not run, and
   `value` is `none`. Otherwise `value` is `some` of the program's value. The check of
   `Database.Valid` at the end is S2's (`Run.checked`): when it fails, `value` is `none`.
   `Run.value : Option α` differs from the guide, which has `α` (owner decision 3).
7. **S2's laws stay.** The run of `send s` is S2's run of `s`: the same outputs, database and
   connection. `Script.run_append`, `Database.Raw.run_append`, `Script.runUntilError`, `Holds`,
   `Empty` and `Fails` keep their meaning, and each statement of their plain words stays true.
   `Holds`, `Empty` and `Fails` take a query with `$x` values, as the guide's
   `SELECT 1 WHERE (SELECT count(*) FROM t) = $n`.
8. **`Env` with a clock.** `Env` holds `clock : Option Clock`: for each statement of a run, by
   its zero-based index, the time in SQLite's Julian-day milliseconds (`SqlState.clock`).
   `Env.default` has no clock. `clockAt "2026-10-20 12:00:00"` is the `Env` whose clock gives
   that time to every statement; its argument is checked where it is written, and a text
   that SQLite's date functions do not read as a time is an error there. Under a clock, a
   statement that reads the clock (`Resolved.Statement.readsClock`) runs with the clock's value
   at its index, so `CURRENT_TIMESTAMP` gives the text of that time; a statement that does not
   read it runs with the value 0, as `runSqlAt` does (`scriptClock`). Without a clock, a
   statement that reads it gives `Output.unmodeled` and ends the run, as in S2.
9. **`Script.run_env`.** For every database, script and environment: if the run of the script
   under `Env.default` does not end at a statement that reads the clock, the run under the
   environment is the same run. The guide says that the elaborator decides whether a script
   reads the environment; `sql` does not resolve at elaboration, and whether a statement reads
   the clock depends on its resolution (a date function of a column or a parameter reads it),
   so the hypothesis is about the run.
10. **The model's run takes the clock.** `runScriptStep` and `runScriptFrom` run a statement
   that reads the clock when the run has a clock, and their laws hold for every clock or for
   a run without one: the agreement with `runSqlFrom` (`runScriptFrom_agrees`, now under the
   clock of `scriptClock`), the append and index laws, and the states before each statement.

## Key points

- **The names of parameters are not in the syntax.** `Syntax.Expr.parameter` holds only the
  number. The text package numbers the `VARIABLE` tokens of each command
  (`numberParameters`, `Translation/Parameters.lean`) and keeps only the first byte and the
  number of each; `translate` (`Translation/Statements.lean`) gives the located statements
  only. The surface needs each statement's parameters with their text, number and range.
- **`$x` elaborates outside the arguments.** The term is a `fun` over the arguments; a `$x`
  elaborated inside it could find an argument `x`. Elaborate each `$x` as an identifier with
  the range of `$x` in the literal (`textRange`, `SqlLiteral.lean`), so that the error is at
  the parameter and the editor's information of `x` comes with it.
- **Named and optional arguments.** Lean takes argument names from the binders of the
  function's type: a probe (2026-10-23, Lean 4.34.1) checked that `def g := fun (amount id :
  Nat) => ...` accepts `g (id := 1) (amount := 15)`. An explicit argument with a default takes
  the next positional argument, so `env` comes after the program (`start.run do ...`).
- **One `run`** (guide open question 15). The probe checked a class from the run's argument to
  `Sql α` with an `outParam` value type and a `@[default_instance]` for `Sql α`: a `String`
  stand-in for `Script` and a `do` block both ran, and a `Coe` to `Sql PUnit` sent a value on
  its own line in a `do` block. A script as the last item of a `do` block whose type is not
  known yet did not elaborate; with a known type, a `Coe` to that type is needed.
- **Checks with free variables.** `Holds`, `Empty` and `Fails` check their query with the
  tactic `check_query`, which runs `decide`. `decide` refuses a goal with a free variable (probe:
  `Expected type must not contain free variables`), and `rfl` proves the same goal. A script
  with `$x` holds a free variable in its values, so the checks of `Holds`, `query`, `single`
  and `clockAt` must not depend on `decide` alone.
- **Programs are data.** `Sql.exec` holds a function, so `Sql α` has no `DecidableEq`; the
  interpreter recurses through the function's result. Measure the kernel cost of the examples.
- **Where the clock is read.** `runScriptStep` (`ScriptRun.lean`) gives `clockUnmodeled` for
  each statement that reads the clock, before it reads `connection.state.clock`, a `Clock`
  (`Nat → Int`, `SqlExecution.lean`) that is 0 in `Database.Raw.connection`. No theorem says
  that a statement that does not read the clock gives one result at every clock value;
  `scriptClock` gives it 0 (`runSqlAt_of_readsClock`). Do so in the run, and `Script.run_env`
  follows from the definition.
- **The agreement theorem.** `runScriptFrom_agrees` compares the run with `sqlTraceFrom` on the
  connection's state, which gives every statement `state.clock`. With outcome 8, the trace's
  state must have the clock of `scriptClock`.
- **Append and a clock.** `Script.runOn_append` and `runScriptFrom_append_constant` need a
  clock that gives the same value at every index, because `p ++ q` moves the indexes of `q`.
  `clockAt` gives such a clock; an `Env` with another clock has the laws for that clock only.
- **The time of `clockAt`.** The model reads a time value with `parseDateOrTime`
  (`Date/Parse.lean`) and computes Julian-day milliseconds with `DateTime.computeJulianDay`
  (`Date/DateTime.lean`); `validJulianDay` (`ClockText.lean`) gives the range. A text of `now`
  reads the clock (`namesClock`) and is not a time. The model has only UTC (`Date/LocalTime.lean`).
- **The guide's types.** The guide's `Code` and `Row` do not exist: `Output.error` holds a
  `Nat`, the model's `Row` is a stored row with a rowid (`Declarations.lean`), and result rows
  are `List (List Value)`. `#eval` shows a value through its derived `ToExpr`, which shows
  constructors; `Value.display` (`OutputRepr.lean`) shows `3`, as `#eval demo.value` needs.
- **Replaced behavior.** Slice 1 of ADR 0019 made `sql r"SELECT ?1"` a script that binds no
  values (its outcome 7, and `GuideScripts.lean`). S3 replaces that meaning. Update the callers
  and the fixtures; keep no second path.
- **Exhaustive matches** over `Output` and `RunStep`; the surface's names under `Belay.Sqlite`.
- **Documentation follows the code.** The surface's README, and at the end the row
  "`Env` with a clock" of ADR 0017's "Deferred, with their triggers", which S3 finishes.
