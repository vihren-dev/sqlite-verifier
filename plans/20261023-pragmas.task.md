## Outcome

Each pragma name is case-insensitive. A schema name (`main.`, `temp.`) stays a frontend refusal.
A pragma that this list does not name stays a frontend refusal, as today.

1. **Check forms.** `PRAGMA integrity_check` and `PRAGMA quick_check`, alone, with a value in
   parentheses or after `=`. The value is a row limit or a table name, as SQLite reads it
   (`sqlite3GetInt32` over the token text without its sign, `pragma.c:1718-1727`): an unquoted
   decimal integer is a limit, and a minus sign is ignored (`(-2)` is 2); 0 is the default, 100.
   A name, or a quoted value such as `('5')`, is a table name; a missing table fails at prepare
   with `no such table: x`. The frontend refuses the other values (a real, a hex integer, an
   integer above 2147483647, `ON`, `DELETE`, `DEFAULT`). The output has one column,
   `integrity_check` or `quick_check`, and no change count.
2. **Check rows.** The row `ok` when no check fails; else one row for each failure, in SQLite's
   order, and at most the limit. For each table, rows in scan order; for each row, in this order:
   - (`integrity_check` only, `WITHOUT ROWID`) `row not in PRIMARY KEY order for t` when the
     primary key of the row equals that of the row before it;
   - for each column in column order, at most one row: `NULL value in t.a`
     for a NULL in a NOT NULL column (also an implied NOT NULL of a `WITHOUT ROWID` key), else
     `non-INTEGER value in t.a` (the type name of `sqlite3StdType`) for a `STRICT` cell that
     does not fit; a `STRICT` REAL column takes an integer;
   - one row `CHECK constraint failed in t` when any CHECK constraint of the table is false;
   - (`integrity_check` only) for each unique index of the table in SQLite's list order:
     `non-unique entry in index i` when the index entry of the row is followed, in index order,
     by an entry with an equal key. The check skips a NULL key term, except in a NOT NULL
     column. Of n rows with an equal key, the n-1 rows that come first in index order fail.
   The names are as declared; an index of a constraint is `sqlite_autoindex_t_N`.
   SQLite skips the column checks of a rowid alias; the model checks it like the other
   columns, and in an admitted database its cell is the integer rowid (`Row.Aliased`), which
   passes. SQLite orders the entries with an equal key by the key that it appends to the
   index: the rowid, or the primary key of a `WITHOUT ROWID` table in the order of the table,
   which are the scan order. The index of a UNIQUE constraint of a `WITHOUT ROWID` table with
   `PRIMARY KEY DESC` is the exception: SQLite appends the primary key in ascending order
   (`bAscKeyBug` in `build.c`), so its equal entries are in the reverse of the scan order. The
   duplicate check uses the order of each index.
3. **Which tables.** The form with a table name checks only that table. The form without one
   checks every table, in the order of SQLite's schema hash table. The model gives the exact
   rows when at most one table gives failure rows; when two or more do, the output is
   `Output.unmodeled` (status file, decision 1).
4. **Laws.** For every database with `Database.Admitted`: `PRAGMA integrity_check` gives the
   one row `ok` exactly when `Database.NotNull`, `Database.ChecksHold`, `Database.TypesFit` and
   `Database.KeysUnique` hold; `quick_check` exactly when the first three hold. The form with a
   limit has the same laws. The form with the name of table t has the same laws with the table
   forms (`Table.NotNull` and the others) of t only, and gives `ok` when another table fails.
5. **`PRAGMA foreign_key_check`**, alone or with a table name (`(c)` or `= c`). The columns
   `table`, `rowid`, `parent` and `fkid`. For each child table with foreign keys, for each row in
   scan order, for each foreign key in `fkid` order, one row when the child key has no NULL and
   no parent row matches: the table name as declared, the rowid (NULL for `WITHOUT ROWID`), the
   parent name as written in `REFERENCES`, and the `fkid` of the key. A parent table that is
   missing makes every row with a non-NULL key fail. The match is the match of the writes
   (`parentFound`). The pragma ignores the setting of `foreign_keys`. A foreign key whose parent
   key has no unique index fails the statement at prepare with
   `foreign key mismatch - "c" referencing "p"`; a missing named table with `no such table: c`.
   Without a table name, SQLite walks the tables in the order of the schema hash table. A
   mismatch fails at prepare, before SQLite reads a row, so one table with a mismatch gives its
   error also when other tables give rows (checked natively). The mismatches of two or more
   tables are the restriction `foreign-key-mismatch-order`; with no mismatch, two or more
   tables with rows give `Output.unmodeled` (status file, decision 1). Laws: when the form without a
   table name succeeds, it gives no rows exactly when `Database.ForeignKeysHold` holds; when the
   form with the name of table t succeeds, exactly when `Table.ForeignKeysHold` holds for t.
6. **`PRAGMA table_info(t)`** (also `= t`, and a quoted name): the columns `cid`, `name`, `type`,
   `notnull`, `dflt_value` and `pk`; one row for each column that is not generated, in column
   order; `cid` counts only these columns. `type` is the declared type as written and dequoted
   (`VARCHAR ( 10 )`, `"x""y"` gives `x"y`), else `''`; a type that is one of the names of
   `sqlite3StdType` in any case is that name in capitals (`int` gives `INT`, `build.c:1532`).
   `notnull` is 1 for NOT NULL and for a key column of a `WITHOUT ROWID` table. `dflt_value` is
   the text of the default as written without the parentheses of `DEFAULT (...)`
   (`ColumnDefault.sourceText`), `NULL` text for `DEFAULT NULL`, and SQL NULL without a default.
   `pk` is the position of the column in the primary key from 1, else 0. A missing table gives
   no rows and no error.
7. **`PRAGMA foreign_key_list(t)`**: the columns `id`, `seq`, `table`, `from`, `to`,
   `on_update`, `on_delete` and `match`; one row for each column of each foreign key, by `id`
   and then `seq`. The ids count the keys newest first: the reverse of the column keys in column
   order followed by the table keys (`CatalogTable.allForeignKeys`). `to` is NULL without a
   column list; `match` is `NONE`. A missing table gives no rows.
8. **Table-valued forms.** `pragma_table_info(x)` and `pragma_foreign_key_list(x)` in `FROM`,
   where x is one text literal: the rows of outcomes 6 and 7, with the hidden columns `arg` (x)
   and `schema` (NULL), which `*` does not show. A name of a hidden column, in an expression, a
   `GROUP BY` term or `USING`, is the restriction `table-function`, because SQLite gives a
   condition on such a column to the pragma as an argument. A cell has no affinity and the binary
   collation: `dflt_value = 5` is false for the text `'5'`. Every other table-valued pragma, and
   another argument form, stays the restriction `table-function`.
9. **`PRAGMA recursive_triggers`**: the query gives one row with the column
   `recursive_triggers`, 1 or 0; `= value` takes the values of `PRAGMA foreign_keys`, has no
   output columns and takes effect also inside a transaction. When the setting is on, a trigger
   fires again while it runs, and the rows that REPLACE deletes fire the DELETE triggers. A write
   whose triggers need more nested frames than the profile's `triggerDepth` (1000) stays
   unmodeled (checked: a chain of 1000 rows succeeds, of 1001 fails). The setting starts from
   the profile.

## Measurement

Over the migrations of corpus-v4 and corpus-v5 (a case's setup reaches the model as its native
tables, `initial`, not as statements): v4 has 31 cases with `PRAGMA integrity_check`. v5 has 280:
`integrity_check` 64, `foreign_key_check` 206 (201 with a table name, 2 without, 3 with a schema
name), `foreign_key_list(t)` 5, `table_info` 1 and `pragma_table_info` of a view 2. No case uses
`quick_check`, a row limit, a table name in `integrity_check` or `recursive_triggers`. Without
the other unmodeled forms, up to 28 cases of v4 and 265 of v5 become clean (upper bounds).

## Key points

- **No corpus case can show a failing check.** No modeled statement reaches a database whose
  constraints fail (ADR 0022, D5), and the recorder admits no `writable_schema` or
  `ignore_check_constraints`. The rows of outcome 2 rest on the Lean examples and the native
  probes below (status file, decision 2). The judge compares the rows of a `PRAGMA` as a bag
  (`native_ordering.py:56`, `judge/outputs.py:41-49`), so the corpus does not check their order.
- **The order of the tables** (status file, decision 1). SQLite walks `pSchema->tblHash`.
  Without buckets it holds the tables newest first; it gets buckets at the fifth entry (with
  `sqlite_schema`), and keeps them after a DROP (`hash.c:267`). Checked: tables `p`, `c1`, `c2`
  give `c2 c1`; with `c3` they give `c3 c1 c2`; eight tables `t1` to `t8` give
  `t8 t7 t6 t5 t1 t2 t4 t3`.
- **Index order and names.** SQLite's list of the indexes of a table (`pTab->pIndex`) is newest
  first, with the REPLACE indexes last (`build.c:4494`). The constraint indexes are numbered in
  the text order of the PRIMARY KEY and UNIQUE constraints, and a duplicate key
  gets no index (checked: `t(a UNIQUE, b PRIMARY KEY, c, UNIQUE(c), UNIQUE(a))`
  has `sqlite_autoindex_t_1` to `_3`). `Catalog.uniqueKeys` (`Resolution/Catalog.lean:25`) puts
  the primary key first and has no index names; check what the catalog keeps of the text order.
- **The laws and the stored forms.** SQLite also checks the stored form of each cell of a table
  that is not `STRICT` (`NUMERIC value in t.a`, `TEXT value in t.a`, `pragma.c:2010`, `2026`).
  `Table.RowsStored` (an Admitted atom) excludes these rows, so the model does not give them.
  SQLite computes a `VIRTUAL` column for its NOT NULL and type checks; the model reads its cell.
  The two agree in each database that the statements reach, but no atom says so (ADR 0022,
  "Not decided here"); the docstrings of the laws say this.
- **Existing checks.** `LiteralData.notNullRows`, `typedRows`, `checkedRows` and `keysUnique`
  give only `Bool`. `RowCheckOrder.lean` and `TableFailure.lean` give the failures of a row for
  the writes, in another order (generated columns first). One definition of each constraint
  must stay (ADR 0022 slice 1, "One definition of each constraint"): build the rows from the
  same row predicates, and prove that no rows mean the atoms. A CHECK cannot fail to evaluate
  (`TableChecks.lean:14`).
- **Data or catalog.** The check pragmas read the rows, so they run at execution time;
  `table_info` and `foreign_key_list` read only the catalog, which resolution knows (the run of
  S2 resolves each statement against its own catalog, `ScriptRun.lean:89`). Today
  `PRAGMA foreign_keys` resolves to a `SELECT` without `FROM` (`Resolve.lean:24`).
  `Resolved.Source` (`QueryForm.lean:30`) has `table`, `each` and `subquery`; a source of rows
  would give the statement forms and the table-valued forms one meaning. The name check
  (`eponymousName`, `Sources.lean:53`) and `eachReference` (`FunctionSources.lean:31`) refuse
  `pragma_` sources today.
- **New statement forms** need arms in each exhaustive match over `Syntax.Statement` and
  `Resolved.Statement`: `QueryOutputs`, `Resolve`, `SchemaScript`, `TransactionSpec`,
  `NamesSpec`, `ResolveStateSpec`, `StatementCatalog` (a new `Kind` first), `StatementOutput`,
  `OutputTable`, `Output`, `PossibleOutput`, `StatementClock`, `Execution`, `ExecutionMessages`,
  `StatementStep`, `FailingConstraints`, `SqlLaws`, `StepCatalogLaws`, `ForeignKeyResolution`,
  `TriggerRules`, `TriggerBodies`, the examples, and `Belay/Sqlite/DbDiagnostics.lean`.
- **Foreign keys.** `ForeignKey` (`Resolution/ForeignKeys.lean:14`) has no stored `fkid`; the
  ids come from `allForeignKeys` reversed. `Catalog.parentLink` (`ParentKeys.lean:124`) gives
  `located`, `mismatch` or `missing`, as `sqlite3FkLocateIndex` does; `ForeignKeyLink.satisfied`
  is false for the last two. The match agrees with the writes (checked: `'1.0'` and `' 1'` find
  rowid 1, a REAL `1.0` does not find the TEXT key `'1'`, a blob finds nothing).
- **Recursive triggers.** The setting lives beside `foreignKeys` (`ResolveState.lean:22`,
  `ScriptRun.lean:31`, `Profile.lean:63`), with `ResolveState.after` and `SqlState.Agrees`.
  SQLite reads it when it prepares a write. The run skips a running trigger
  (`TriggerRun.lean:145`); REPLACE deletes fire nothing (`TriggerClosure.lean:83`). The
  closure resolves each trigger once, and fuel ends as unmodeled (`ForeignKeyWrites.lean:40`).
  The depth error stays unmodeled: SQLite keeps the rows of the failed statement inside a
  transaction (checked: the 1001 rows of the failed INSERT stay), as its statement journal
  decides. The
  recorder admits a setting only at the profile's value (`execution_profile.py:79`), and
  `profile_scope.py:28` refuses a profile with the setting on; this task makes it accept such a
  profile (status file, decision 3).
- **Checked natively** (3.51.0 shell, `writable_schema` for the broken databases): the rows of
  outcome 2 for tables `t(a NOT NULL, b CHECK (b > 0), c, d INTEGER PRIMARY KEY)` with a unique
  index on c, a `STRICT` table and a `WITHOUT ROWID` table; `(2)`, `(-2)`, `(+1)`, `= 1`, `(0)`,
  `(1.5)` (1 row), `(0x2)` (2 rows), `('1')` and `(2147483648)` (no such table); outcomes 5
  to 9, the mismatch message, and `pragma_integrity_check(2)` (`no such table: 2`, at run time).
