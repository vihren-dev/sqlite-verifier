## Scope

A user proves a fact about every database. The fact is `Holds`, `Empty` or `Fails` of a query,
or "this script succeeds where this query holds". The proof uses lemmas that turn the query into
Lean logic about the catalog and the rows. The guide is the target. Where it is false over every
database, the guide changes (a local commit of the product repository, as in S2 and S3), and the
status file records why.

Out of scope, each recorded in ADR 0017 or in the status file:
- Counterexamples: `#sql_check`, `sql_refute`, the sampling instances, the background check (S5).
- Triples, the `Std.Do` instance of `Sql`, `holds`, `ifOk`, `andOk`, `≈` and its patterns,
  footprints, `sql_commute`, `sql_run`, `before` (S6). In S4, `succeeds where` is a plain
  proposition. S6 proves that it is the triple of the guide. The effect, frame and
  specification lemmas (`rows_insert`, `rows_frame`, `send_insert_spec`): only triples read them
  (status file, decision 1).
- `sql_auto` and `#explain` (decision 5). `sql_file`, `sql_module` (S7). A clock for `Holds`:
  it keeps S2's meaning, so a query that reads the clock does not hold.
- New model behavior. S4 adds theorems and surface definitions; no prediction changes.

## Outcome

1. **A claim over every database is a Lean statement.** For a query `q` (a script of one
   read-only statement, with `$x` values or arguments) and any predicate `P`,
   `∀ db : Database, P db → Holds q db` elaborates, and so do `Empty` and `Fails`. S2's
   definitions and their argument check stay. `decide` does not prove such a claim (see "Key
   points"). A proof uses outcomes 2 to 6.
2. **The bridge.** For every database and every query `q`, `Script.outputOn q db` is given in
   the model's terms: the resolution of the statement against `db.raw.catalog`
   (`resolveStatement`); an `Output.error` for a prepare error or for a run error of the
   statement (aggregate overflow, a function error and the others of `Output.ofStep`);
   `Output.unmodeled` for a restriction, a clock read, an unknown counter or a statement that is
   not `ready`; otherwise `Output.ofResults` of `Resolved.Query.possibleOn`. `Holds`, `Empty` and `Fails` each get an
   equivalence over these terms. For results `rs`, `(Output.ofResults rs).hasRows` holds exactly
   when `rs` is not empty and each result has a row. `hasNoRows` is the same for no row.
3. **Query lemmas.** For each query form of the list below, the three equivalences `Holds q db ↔
   …`, `Empty q db ↔ …` and `Fails q db ↔ …` in Lean logic. The right sides name the catalog
   (`Catalog.findTable`), the rows of the table, and the model's resolved expression and its
   evaluation on a row. Each lemma says when the query does not hold: a missing table or column (an
   error), an aggregate overflow (an error, `Query.fails`), and an expression that may fail on some
   row (`Output.unmodeled`, `Query.mayFail`), for which none of the three holds. The forms are
   those of the guide's table and of level 2, and no more:
   - a query without `FROM`: `SELECT e`;
   - `SELECT 1 FROM t WHERE p`;
   - `SELECT 1 WHERE [NOT] EXISTS (SELECT 1 FROM t WHERE p)`, and `x IN (SELECT …)`;
   - `SELECT 1 FROM pragma_table_info('t') WHERE name = 'c'`;
   - `SELECT 1 WHERE (SELECT count(*) FROM t) <op> $n`;
   - `SELECT 1 WHERE NOT EXISTS (SELECT 1 FROM t GROUP BY k [COLLATE c] HAVING count(*) > 1)`;
   - `SELECT sum(c) FROM t WHERE …`, for its `integer overflow` fault.
4. **Expression laws.** The lemmas that turn the resolved expression of outcome 3 into Lean
   logic for the forms that the examples use: a column, a literal, a parameter, a comparison with
   affinity and collation, `AND`, `OR`, `NOT`, `IS NULL`, `[NOT] BETWEEN`, `COLLATE`, `count(*)`
   and `sum`. They extend S2's value laws. They are in one simp set, `sql_simp`, with the `grind`
   attribute where `grind` uses them (decision 5). A simp set is enough: S4 adds no tactic.
5. **Schema facts.** A fact of the schema that SQL states with `pragma_table_info` is a fact
   of `db.catalog`: the rows of `pragma_table_info('t')` are the columns of the table
   (`Catalog.tableInfoRows`) that are not generated, with their name, declared type, NOT NULL
   flag and primary-key position; a generated column has no row. The lemma says that the name test `name = 'c'` is a case-sensitive text
   comparison, and that the table lookup ignores ASCII case.
6. **A unique lookup gives at most one row.** For every `db : Database`, a table `t` with a
   unique key of one column `c` (no filter), and a value `v`: at most one row matches `c = v`.
   The statement is about the query `SELECT 1 WHERE (SELECT count(*) FROM t WHERE c = $v) <= 1`.
   The proof reads `db.unique` (`Database.KeysUnique.lookup`), and for a rowid alias
   `db.rowid_unique`. The lemma states what `c = v` does with affinity (it matches the rows that
   are equal to the value after the affinity of `c`) and with collation: the bound holds only when
   the comparison uses the collation of the key. A column `COLLATE NOCASE` with a unique index
   `COLLATE BINARY` can hold `'a'` and `'A'`, and `c = 'a'` then matches both rows, so the
   lemma has the equality of the two collations as a hypothesis.
7. **`Succeeds`.** The primitive `Succeeds S P` takes a script or a program `S` and a predicate
   `P : Database → Prop` (any Lean proposition). It states: for every database `db` with `P db`,
   and for every environment of decision 2, the outputs of `db.run S` have no `Output.error`,
   and no output ends the run (`List.allOk`). Thus a run that ends at `Output.unmodeled` is not a
   success. `S succeeds where G` is `Succeeds S (Holds G ·)`, and `S succeeds` is `P := True`. The
   argument `G` is checked as `Holds` checks it. For a program, the definition follows every
   branch: for an `Output.oneOf`, it continues with each result (decision 3). `send s` succeeds
   exactly when the script `s` does. The laws: `Succeeds` is monotone in `P`; `Sql.pure` succeeds;
   a script `p ++ q` succeeds on `db` exactly when `p` succeeds on `db` and `q` on `(db.run p).db`
   (under the conditions of `Script.run_append`).
8. **Success of statements.** Lemmas of the forms that level 2 uses: a query succeeds exactly
   when `Fails` does not hold and the run does not end; `CREATE [UNIQUE] INDEX` succeeds exactly
   when the table exists, the name is free (no table or index of that name, and it is not
   reserved), the terms and filter resolve, and for a unique index no two rows conflict on the
   new key (`LiteralData.keyEqual`). The lemma relates the last condition to the `GROUP BY`
   form of outcome 3: a query of that form that holds shows that no two rows conflict.
9. **Program laws.** `Sql` is a `LawfulMonad`. The run of `p >>= f` is the run of `p`, then the
   run of `f` on its value, at the next index, on the connection that `p` left (S3 left these laws
   to S4). The run of `send (p ++ q)` is the run of `send p` then `send q`.
10. **The run needs no check.** After ADR 0022 slice 4, `Run.checked` takes its valid branch
    for every `Database`, program and environment (decision 4): the database of the run is the
    one that the model's run reaches, and its outputs are the model's outputs, with no output
    for an invalid result. The run gives its `Database` from that theorem, and the decision of
    `Database.Valid` goes (decision 4). Outcomes 7 and 8 need only the theorem: with it, a proof
    shows that the valid branch of `Run.checked` is taken (ADR 0022, D5), whether the decision
    stays or goes. Without the theorem, `Succeeds` cannot be proved, because the else branch
    ends the outputs with `Output.unmodeled`.
11. **The guide's examples are true.** The examples of "Queries as propositions" and "Level 2"
    elaborate after the guide's changes, and their proofs check. These claims are false over
    every database as the guide writes them (checked natively, 2026-10-24, see the status
    file): `uniqueEmail_ok` (a table or index of the name `customers_email` makes the
    `CREATE` fail) and `balance_ok` (a `ledger` without `account` fails to resolve, and a TEXT
    column `cents` holds ten or more values `'0999999999999999999'`, which pass the bound as text and sum as
    integers). The status file records the corrected claims (decision 6).

## Key points

- **A free `db` cannot be reduced.** Measured 2026-10-24 (Lean 4.34.1): `decide` and `decide
  +kernel` refuse a goal with a free `db` (`Expected type must not contain free variables`). `rfl`
  proves `Holds (sql r"SELECT 1") db`, but fails with `maximum recursion depth has been reached`
  for `SELECT 1 WHERE 1 = 1`. So every proof goes through the lemmas, with `simp`. The unfolded
  goal is `runScriptFrom` → `runScriptStepWith` → `resolveStatement` → `statementClock` →
  `counters.firstUnknown` → `statementRun.ready` → `Output.ofStep` → `possibleOutput`
  (`Model/ScriptRun.lean`, `Output.lean`, `PossibleOutput.lean`, `PossibleResults.lean`). The
  split on `findTable` is the first case of every lemma.
- **Resolution on a free catalog.** The lemma of `SELECT 1 FROM t WHERE p` cannot compute
  `resolveSelect` for a free table. It takes the resolved expression as a hypothesis, `resolve …
  = .ok e`, and outcome 4 gives it for each form of `p`. Column lookup ignores ASCII case;
  `name = 'c'` in `pragma_table_info` does not.
- **`Holds` also requires no fault.** The guide says that `holds_where` holds "exactly when the
  table exists and some row of it makes `p` true". This is false when `p` fails on another row.
  Native check: with rows `1` and `-9223372036854775808`, `SELECT 1 FROM t WHERE abs(x) = 1`
  returns a row and then `integer overflow`. The model gives `Output.unmodeled` for it. Its faults
  are `Fault.none`, `.may` and `.must` (`ExprFault.lean`); `.may` gives `Output.unmodeled`, so
  none of the three holds.
  `Query.mayFail_of_plain` (`QueryPlainLaws.lean`) gives no fault for plain expressions.
- **`Output.ofResults` sorts and removes duplicates.** The equivalence of outcome 2 needs that
  `eraseDups` and `stableSort` keep membership (`stableSort_perm`, `QueryLaws.lean`), and that an
  empty list of results gives `Output.unmodeled`, which is neither rows nor empty.
- **GROUP BY and key conflict.** `GROUP BY k COLLATE NOCASE` groups NULLs together. A key
  conflict never involves NULL (`keyCellsEqual`, `LiteralData.lean`). So the query of outcome 3
  is stronger than needed: two NULL emails make it false, and the index still succeeds. The
  lemma of outcome 8 is one-way here, and a test shows the NULL example. NOCASE folds ASCII only.
- **The name of an index is not readable in the model.** `sqlite_schema` is a restriction
  (`RestrictionKind.systemTable`), and `pragma_index_list` is not modeled. A claim that needs
  "the name is free" states it in Lean about `db.catalog` (`Catalog.find`), through the predicate
  of `Succeeds`. `resolveCreateIndex` (`Resolution/Definitions.lean`) lists the cases; a trigger
  of the same name does not clash.
- **Environments.** `Succeeds` quantifies over the environment (decision 2). `Script.run_env`
  and `Sql.run_env` (S3) show that, for a script that reads neither the clock nor a counter, the
  default environment is every environment. `Env.default` has no clock and no known counter.
- **What S4 needs from ADR 0022 slice 4** (its task file, outcomes 3 to 5): the corollary that
  `runScriptFrom` keeps `Database.Valid` for the start database and its snapshot, with the
  profile of `runContext`; the same for the surface's `Sql.runFrom` (its decision 6, option a));
  the Admitted atoms as fields of `db.valid` (rows wide, rows stored, rowids), which outcome 3
  reads. S4 does not need its frame lemmas or its resolver facts directly. Its decision 5 became
  a) on 2026-10-24: repeated key columns are modeled. The unique lookup of outcome 6 takes a key
  of one column, so it is not affected. Outcomes 1 to 6 do not wait for slice 4. Outcomes 7, 8 and 10, and the
  examples of outcome 11 that use `Succeeds`, need its corollary.
- **Existing laws to reuse.** `Query.mem_filtered`, `countRows_eval` (`QueryLaws.lean`),
  `Database.KeysUnique.lookup` (`KeysUniqueLookup.lean`), `Run.checked_modeled`, `Script.run_append`
  (`RunLaws.lean`), `Sql.runFrom_send`, `Sql.runFrom_env` (`ProgramLaws.lean`),
  `Catalog.tableInfoRows` (`Resolution/PragmaRows.lean`).
- **Grouping the work.** The model gets the bridge and the query lemmas if they speak only of
  model terms; the surface gets `Succeeds` and the guide's names. New model modules stay out
  of the files that the mutant scripts copy.
- **Size and form.** Files stay below 200 lines. Docstrings are Verso, with plain words for
  each proposition and a sketch for each proof over 20 lines.
- **Documentation follows the code.** The surface README, and the deferred row of ADR 0017 for
  the theorems that replace the check of a run.
